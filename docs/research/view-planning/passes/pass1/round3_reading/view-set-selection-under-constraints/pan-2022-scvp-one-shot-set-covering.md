## Core method / idea

SCVP is a **learned one-shot view-set predictor**: given a single occupancy-grid observation of a partially-unknown object, a 3D-CNN classifier directly outputs a binary vector over a **fixed 32-candidate view space** (positions on the upper hemisphere placed via Spherical Codes — a Tammes-style max-min-distance sphere packing, MA-SCVP §III-C citing ref [68]) marking which of the 32 candidates should be visited. No iterative next-best-view (NBV) loop, no per-step utility re-evaluation, no runtime ray-casting search — the whole view sequence is emitted in a single forward pass, then globally path-planned (open TSP-like) over the selected views.

The predictor is trained by **automatic label generation via exact set-cover optimization (SCOP)**: given known 3D mesh models (the training-time privileged information), for every training input case the paper virtually images all 32 candidates, computes each candidate's covered-voxel set, and solves the classical set-cover ILP —
`minimize Σ z_v  s.t.  Σ_{v: e∈v} z_v ≥ 1 ∀e∈U_rest, z_v∈{0,1}`
(MA-SCVP Eq. 4, explicitly stated to be the same formulation "as in our previous work SCVP [6]") — via the **Gurobi Optimizer**, chosen because "it takes the lead in the benchmark of linear programming solvers" and because "the problem size of SCOP is not too large (the number of voxels and views is not too many), [so] Gurobi can solve SCOP in an acceptable time for labeling (**less than 10 seconds**)." The network is trained to imitate this exact-optimal minimum cover, per training instance, at scale (thousands of instances).

The network's **auto-stop mechanism** is not a separate runtime threshold rule at all — it *is* the classification output itself: because training labels are literal minimum-set-cover solutions (not "cover until 95%" or "gain < ε" heuristics), the number of 1-bits the trained classifier emits for a given input *is* the predicted minimal covering set. This is contrasted explicitly against iterative NBV baselines' "hand-crafted heuristic stop criterion" (MA-SCVP §I, §V-E1).

**Loss function (SCLoss):** because the minimum-cover ground-truth mask is heavily class-imbalanced (few 1s — typically ~10/32 — among many 0s), SCVP introduces a hyperparameter λ to reweight positive vs. negative cross-entropy terms: `SCLoss = -(1/32) Σ_i [(1-s_i^gt)·CE_i + λ·s_i^gt·CE_i]` (MA-SCVP Eq. 7, explicit: "As shown in SCVP [6], the 1's and 0's in the ground truth mask have different importance to the network training"). λ is chosen by grid search maximizing F1 on a held-out set, "following the strategy outlined in SCVP."

**Network I/O:** input is a 32×32×32 occupancy grid (an OctoMap crop, dynamically resolution-scaled to the object's bounding-sphere size — SCVP itself used a *fixed* resolution of 0.00625 m for objects resized to a max 0.10 m bounding sphere, later found brittle for small objects and replaced by dynamic resolution in MA-SCVP); output is a 32-bit vector, one bit per fixed candidate view index. Candidate 32 is deliberately small — smaller than NBV-Net's 14-on-hemisphere or PCNBV's 33-on-whole-sphere baselines, chosen as "sufficient to observe all visible areas" in a tabletop setting.

## Concrete results / numbers (as re-measured in MA-SCVP's controlled re-evaluation of SCVP [6])

- **Simulated benchmark, 3,000 test cases (MA-SCVP Table VII):** SCVP achieves RV (required views) = **9.61 ± 0.96**, VSC (visible surface coverage) = **96.12% ± 6.29**, MC (movement cost, path length) = **2.28 ± 0.15 m** — versus iterative-NBV baselines (APORA+Mov, RSE+Mov, MCMF+Mov, GMC+Mov) needing RV ≈ 11.3–12.5 for VSC 95.5–97.5%, i.e. SCVP uses ~2 fewer views for comparable coverage.
- **Inference time (MA-SCVP Table VIII, 3,000 tests):** SCVP = **0.112 ± 0.121 s** per one-shot inference (vs. NBVNet 0.006 s, PCNBV 0.099 s, both of which are *per-step* costs multiplied by ~7–11 iterations for the search-based baselines — SCVP pays this cost once).
- **Real-world, UR5 arm + Intel RealSense D435 eye-in-hand, 60 tests (MA-SCVP Table X):** SCVP = RV **10.20 ± 0.95**, VSC **95.88% ± 4.28**, MC **1.28 ± 0.15 m**, RT (total reconstruction time) **82.2 ± 11.7 s**.
- **View-count vs. object complexity (MA-SCVP Table XII, "0-NBV+SCVP" row = pure SCVP):** objects requiring 4–7 covering views (314 test cases, "simple") reach VSC 99.67%; 8–12 views (1,729 cases, "medium") reach 97.85%; 13–16 views (957 cases, "complex") reach only 91.83%. **No closed-form relationship between object geometry and view count is given** — the count is whatever SCOP's exact solver returns for that specific object/candidate-set instance; MA-SCVP itself *uses the SCOP-solved view count as its complexity metric*, i.e. treats "how many views does this object need" as an empirical/optimization output, not a predictable closed form.
- **Training/label-generation solve time:** Gurobi solves each per-instance SCOP in **<10 s** (32 candidates × occupancy-grid-sized voxel universe) — the concrete number for "is exact ILP tractable at this scale."
- **Dataset:** Stanford 3D Scanning Repository + Linemod + HomebrewedDB + Clutter mesh models, object sizes normalized to [0.05, 0.15] m bounding sphere, **70 total distinct models split 40 train / 30 test** (unknown-at-test-time objects).

## Load-bearing assumptions

- **The coverage predicate is pure binary visibility** — a voxel is "covered" if any ray-cast from a candidate view hits it in the occupancy grid, full stop. No incidence-angle, orthogonality, distance, or resolution weighting anywhere in what MA-SCVP recaps of SCVP's SCOP formulation (Eq. 4) or metric (VSC, Eq. 8). Same gap as already found in ObjView-Bench (2026) — this is now a second independent confirmation that the field's default "set cover for view planning" framing is quality-blind by default.
- **Candidates are placed uniformly over the whole object via Spherical Codes (Tammes packing), not conditioned on local surface geometry at all.** This is exactly the "uniform sphere with no relation to inspected object geometry" pattern our framing doc identifies as the problem to fix — SCVP is not a counter-example, it is a sophisticated instance of the same pattern (32 evenly-spaced hemisphere points, fixed regardless of whether the object is boxy, cylindrical, or organic).
- **The problem is framed as reconstructing an *unknown* object from partial single-view input** — the network's whole reason to exist is to predict where the *unseen* surfaces probably are, using a shape prior learned from the training corpus, because at inference time there is no full model to solve SCOP over directly. Full-model SCOP (exact ILP) is only ever run offline, as a training-label oracle, never as the deployed policy.
- **No kinematic/reachability modeling in the candidate space design or the network itself.** The 32-candidate hemisphere is treated as a free-flying-camera abstraction at design time; reachability only becomes a real problem when the same lab deploys the system on an actual UR5 arm (in the MA-SCVP follow-up), and even then it is patched, not modeled (see below).
- **Ground-truth surface for evaluation is a separately-captured, multi-view-fused reference point cloud** (collected by "sensing the entire view space and voxelizing to 0.002 m"), not the same defective single-survey cloud the planner itself would work from — small calibration offsets are handled by nearest-neighbor voxel matching, a much lighter noise regime than our ~4 cm fused-vs-single-view offset.

## What transfers to our setting

- **Direct, load-bearing precedent for Q3 ("can we just solve it exactly at our scale?").** SCVP is the strongest evidence yet found in this branch: at 32 candidates and a modest voxel-grid universe, exact ILP set-cover via Gurobi solves in under 10 seconds *per instance*, run at the scale of an entire training-label-generation pipeline (tens of thousands of instances across 70 objects × many rotations/partial-input cases). This is not a toy demonstration — it's a production data pipeline built on the assumption that exact ILP at this problem size is cheap. **The critical nuance for us:** SCVP still needs a learned network at deployment, but *only because its problem is genuinely unknown-object reconstruction* — the object being viewed is not the object whose model was solved. **We do not have that constraint** — our survey point cloud IS the object geometry at planning time, known and complete (modulo real defects), which is exactly the condition under which SCVP's own authors say offline-exact-ILP is the right tool. This converts Q3 from "is ILP tractable" (yes, clearly, per SCVP's own engineering choice) to "do we even need the learned layer at all" — SCVP's raison d'être (predicting invisible surfaces from partial views) doesn't apply to us, so the strongest reading is that we should skip the network and solve set-cover (or a quality-weighted variant) directly online.
- **A second independent, earlier-dated confirmation that the field's canonical framing is literal minimum-set-cover** (Definition 5 / Eq. 4 in MA-SCVP, inherited unchanged from SCVP 2022, itself following Kaba et al.'s SCOP formulation) — reinforces Q1's finding from ObjView-Bench, now traced one hop further back to its likely origin in this literature line.
- **Concrete, checkable numbers for Q6/Q14** ("how many views, what set sizes do methods actually emit"): mean 9.6–10.2 views out of 32 candidates (≈30% of the full hemisphere) for generic tabletop-scale objects, empirically ranging 4–16 by object complexity. This is real evidence that minimal-set output sizes for tabletop objects cluster in the single-digit-to-teens range, not hundreds — useful as an order-of-magnitude sanity check for our own primitive-level view budgets, even though the underlying objects are not primitives.
- **A concrete, mechanistic description of "SCVP's learned auto-stop" for Q15**, beyond the one-line gloss in the framing doc: the stop is not a separate rule but an emergent property of training on exact-minimum-cover labels with an imbalance-corrected loss (λ-weighted SCLoss) — i.e., "predict membership in the optimal cover" *is* the minimality mechanism. Worth citing precisely if we consider a similar approach: this only works because the *labels themselves* are already minimal (solved by ILP), so the network is distilling an optimizer, not inventing minimality on its own.
- **RQ4's generate-then-select framing is directly instantiated and explicitly justified here**: SCVP binds every network output bit to one fixed candidate-view index specifically *because* "the SCOP is solved in such a fixed candidate view space" (MA-SCVP, discussing the same design in SCVP) — i.e., enumeration-first is a hard requirement of formulating the problem as a fixed-length multi-label classification at all, not an incidental convenience. This is a clean, mechanistic answer to why "generate then select" earns its keep for a learned/optimization-based selector: the discrete index *is* the representation the optimizer and the network both need.
- **A genuinely useful, named real-hardware precedent for Q11's platform**: the MA-SCVP real-world system uses a 6-DOF UR5 arm (same family as our UR5e) with an eye-in-hand Intel RealSense D435 (same sensor family as our D405) in a tabletop reconstruction setting — the closest hardware analog to our platform found in this branch's reading so far, closer than ObjView-Bench's undocumented robot.

## What does NOT transfer, and why

- **Reachability handling is essentially absent, and this is a first-class negative finding for Q9/Q10.** SCVP's candidate space is designed as an idealized free-flying-camera hemisphere with no kinematic constraints. When the same authors deploy the system on a real UR5 arm (MA-SCVP §V-F), they hit exactly our problem — "some candidate view positions may be unreachable due to [joint] constraints" — and their fix is **not** any of the four fallback-ladder rungs in our branch's Q9 framing. It is a blanket, uniform hack applied to the *entire* candidate set regardless of individual reachability: **"we adjust the candidate view positions by moving them up by 0.008 m to ensure reachability."** No per-candidate IK check, no capability map, no re-optimization in an admissible region, no defer-and-retest — just a single fixed vertical offset tuned once for their rig. MA-SCVP's own discussion section names this as an **unsolved limitation, not a design choice**: *"the candidate view space is pre-defined, and the network output is bound to a certain candidate view. This does not allow the system to drop some unreachable candidate views, such as due to obstacles and robot workspace. A possible solution is using a regression network and training it with the state of unreachable views"* — i.e., as of the 2024 follow-up, this remains an acknowledged open problem in this exact lineage, proposed as future work, not solved. This directly answers part of Q10: neither a capability map nor per-candidate IK post-filtering is used anywhere in the SCVP/MA-SCVP line; reachability is handled by neither of the mechanisms our branch is evaluating, but by a third, cruder approach (global geometric nudge) that we should probably not adopt but should cite as a documented failure mode to avoid.
- **No IK multiplicity or Cartesian-vs-joint-space discussion at all (Q12 unaddressed)** — the view representation is a 5-DOF position+orientation ("pointing to object center") with a free 6th rotational DOF about the optic axis, resolved however the downstream motion executor chooses; there is no mention of multiple UR5 IK branches, joint-limit-driven infeasibility, or how the free rotational DOF interacts with reachability.
- **No measurement of which candidates get excluded or whether exclusion is systematic (Q13 unaddressed)** — the paper only reports that adjustment-by-offset "ensures reachability" in aggregate; it never reports a reachable/unreachable count or fraction, and never checks whether, e.g., near-table or steep-elevation candidates are the ones lost.
- **The central premise — reconstructing an *unknown* object from partial geometry — does not match our setting**, where the object is already fully surveyed before view selection happens (Q16's framing). SCVP's entire value proposition (a network that has learned a shape prior to guess where currently-invisible surfaces probably are) is answering a question we don't have: we are not inferring unseen geometry, we are choosing the best vantage points on *already-measured* geometry. If we wanted to use SCVP-style learned selection at all, we'd be repurposing a shape-completion-flavored architecture for a strictly easier, fully-observed selection problem where exact optimization (per the Q3 point above) is directly available instead.
- **Training/eval objects are generic scanned meshes (Stanford repo, Linemod, HomebrewedDB, Clutter) with no primitive/CAD-class taxonomy** — no box/cylinder category, no inspection framing, no defect modeling. One more independent negative data point (third, after ObjView-Bench and the framing doc's own gap analysis) that primitive-decomposition-conditioned view planning is absent from this literature line (relevant to Q18/Q20).
- **No orthogonality/incidence-quality criterion anywhere** (Q7 unaddressed) — consistent with ObjView-Bench; SCOP's coverage predicate in this line of work has never, across two generations of the same method (SCVP → MA-SCVP), incorporated a view-quality or incidence term. If we adopt SCOP-style set cover, the quality gate has to be added by us from scratch.
- **Ground truth for training labels requires full 3D mesh models** (privileged, clean, watertight-ish geometry from curated 3D scan repositories) — not a self-acquired, defective survey cloud with per-view depth dropout and multi-mm pose error. This reinforces (does not newly discover) the gap already flagged for ObjView-Bench: nobody in this specific literature line plans from a defective self-acquired cloud in the way our Q17 asks.
