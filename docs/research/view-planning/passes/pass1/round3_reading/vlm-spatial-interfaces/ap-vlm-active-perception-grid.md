- Selected as closest published prior art: a virtual 3D grid overlaid on the image from which a zero-shot VLM (GPT-4o) picks the next viewpoint for a UR5/Franka with an in-hand camera.

## Core method

**Architecture (Sec. III, Fig. 2).** One GPT-4o instance plays two roles at every step, both operating on the *same* grid-annotated image:
- **Perception Analyzer** — outputs a binary signal `Z`: is the current observation sufficient to answer the query? If yes, terminate and answer.
- **Active Perception Policy (APP)**, `π(a_t, ζ_{t+1} | x_t, õ_t, ζ_t, o_0)` — if not sufficient, picks the next action `a_t` (a grid vertex, optionally + rotation) referencing the same annotated image.

There is **no separate blind orchestrator + vision-subagent split** — this is a single seeing agent that both judges sufficiency and picks the next view, conditioned on the *current* annotated frame `õ_t` and the fixed *home* frame `o_0` (except in the `3DxN` ablation, which drops `o_0` from context). Knowledge state `ζ = {η, κ}`: `η` = initial-prompt context (constraints/goals), `κ` = cumulative history (notably, visited vertices — a simple non-hierarchical memory to prevent revisits). Max 10 action iterations per episode (hard cap); no numeric confidence threshold is given despite the paper also describing termination as "the VLM confidently answers... with a high certainty score" (Sec. III-A, Termination Criteria) — this phrase is never made quantitative anywhere in the text; it sits inconsistently next to the earlier "binary signal Z" formulation (Sec. III, Problem Formulation). Treat the stopping rule as **uncalibrated / heuristic**, not a defensible threshold.

**Enhanced Observation / grid construction (Sec. III, "Enhanced Observation").** The grid is **not derived from the object or any scanned geometry**. It is anchored to the robot's **workspace origin** `(-0.3, 0.1, 0)`, tracked via **9 ArUco fiducial markers** placed around the workspace (redundant so ≥1 is always visible), with vertex poses `V_v^M` in the marker frame transformed to the robot base frame via `V_v^B = T_C^B · T_{M_id}^C · V_v^{M_id}` (Eq., Sec. III) — `T_{M_id}^C` from camera intrinsics/marker pose (OpenCV-style solvePnP, implied), `T_C^B` from robot forward kinematics. Grid vertices are projected onto the live 2D RGB image every step and each vertex is text-labeled `(x;y)` (Sec. III, "Each vertex in the 3D grid is annotated along the x and y axes in the format (x;y)"). **The paper never states whether these labels are metric coordinates or grid indices**, and I could not confirm from the extracted text or figures which — this is a genuine documentation gap, flagged rather than guessed.

**Eight action-space variants (Sec. III, "Action"), the paper's own ablation, home pose `o_0=(-0.1,0.3,0.8)`:**
- `NAP` — no active perception (baseline: answer from home view only).
- `2DNA` — 2D grid, vertices 0.2 m apart, 0.1 m above table, **unannotated**.
- `2DA` — same 2D grid, **annotated** vertex coordinates.
- `3DD` — 3D discrete: grid over a 0.6×0.6×0.3 m cube, height layers 0.1 m apart, move to a vertex.
- `3DC` — 3D continuous: move to any point inside the same 0.6×0.6×0.3 m cube (not vertex-snapped).
- `3Dx` — `3DC` + discrete ±35° rotation about the camera/robot x-axis.
- `3DxN` — `3Dx` but the home-view image `o_0` is **withheld** from VLM context (ablates the value of keeping the home frame as an anchor).
- `3Dxy` — `3Dx` + discrete ±35° rotation about y as well (2-axis rotation menu).

Grid vertices map to **pre-calibrated** robot-base coordinates (Sec. III, last line of "Action") — i.e., feasibility/reachability of each vertex is not dynamically checked against IK/collision at presentation time (see failure modes below).

**TGCSR (Kwon et al. 2024) comparison (Sec. AP-VLM (best variant, `3Dx`) vs TGCSR: Scene 1 (golf ball in mug) 5/5 vs 0/5; Scene 2 (strawberry in cup, fully hidden from all 5 fixed views) 5/5 vs 0/5; Scene 3 (Lego in a cup inclined close to the table) 1/5 vs 0/5 — **AP-VLM itself struggled here too** ("AP-VLM struggled to find an optimal viewing angle," Sec. V).

**Explicit qualitative failure note (Sec. V, Discussion, verbatim):** "the VLM occasionally struggles to handle combined orientation actions around both the x and y axes; the VLM adds x or y-rotations when both or at least one of them are not required. The VLM seems to get more confused with multiple options."

**Explicit limitations (Sec. V, last paragraph, verbatim):** "The current AP-VLM framework is limited by discrete orientation adjustments, which hinder the robot's ability to inspect inclined or hollow objects that require precise front views. Sometimes, the actions are out of reachable robot workspace."

No grid-density/resolution sweep is reported (spacing is fixed per variant: 0.2 m for 2D, 0.1 m height layers / cube fixed at 0.6×0.6×0.3 m for 3D) — no ablation on how many vertices are shown at once.

## Load-bearing assumptions

- **The grid is anchored to the robot's workspace, not to the object.** It is a fixed cube/plane relative to a marker-calibrated origin `(-0.3, 0.1, 0)`, entirely independent of object shape, pose, or geometry — this is the *identical* failure mode our framing doc names as the core problem with the current `{h,v}` viewsphere ("constructed with no relation to the inspected object's geometry"). AP-VLM does not solve this; it is an instance of it.
- **No 3D reconstruction, no point cloud, no depth at all.** Despite using an Intel RealSense RGB-D camera, the paper states plainly (Sec. IV): "The camera provided real-time RGB data... (we did not use depth)." All spatial grounding comes from ArUco fiducial tracking + robot forward kinematics, not from vision-derived or scanned geometry.
- **Task is occlusion/containment resolution ("what is inside X"), not surface-defect inspection.** Success = any view that resolves visibility into a cavity; there is no notion of "the most orthogonal view of a given external surface." The optimization target differs from ours even though the view-selection *mechanism* (grid → VLM picks vertex) is structurally the same problem shape.
- **Feasibility of grid vertices is not dynamically checked.** Vertices map to pre-calibrated base-frame coordinates; the paper's own limitations paragraph admits the robot sometimes gets commanded to unreachable positions — there is no IK/collision pre-filtering, no affordance scoring, no visible/greyed-out-infeasible marking.
- **Rotation granularity is a fixed, apparently arbitrary 35° step** — not derived from task or object geometry — and Scene 3 (steep incline near the table) is exactly the case where this granularity fails to reach the needed viewing angle.
- **Zero-shot GPT-4o, no fine-tuning, no in-context examples reported.** Exact prompt text (system prompt, output-format instructions, any few-shot exemplars) is **never given** in the paper — confirmed by direct read, not just a WebFetch artifact. This is a real reproducibility gap: we cannot recover *how* the VLM was told to read `(x;y)` labels or format its answer.
- **N=10 trials/scene/variant (UR5), N=5 trials/scene (Franka vs TGCSR), no variance reported.** Treat every SR number as a coarse point estimate.

## What transfers to our setting

- **Direct, measured evidence of a compositional/option-count penalty (Q3, Q9).** Adding a second rotation axis to the menu (`3Dx`→`3Dxy`) drops SR from 0.8→0.5 (Scene 1) and 0.5→0.1 (Scene 2), despite `3Dxy` being a strict superset of `3Dx`'s capability (it can always choose zero y-rotation). The authors' own diagnosis is explicit: the model "adds x or y-rotations when... not required... gets more confused with multiple options" (Sec. V). This is a clean, citable, real (if small-N) data point that the failure is **not raw geometric capability** but **menu-induced spurious activation of extra axes** — supports designing a one-parameter-family-per-turn interface (RQ3/RQ4) over a combined multi-axis menu, and is good ammunition for the "count vs. distinctiveness" question: here the count didn't even grow (still one action per step), only the *dimensionality of the options within one action* grew, and that alone was enough to hurt.
- **A working precedent for the "seeing option" that sidesteps the render-from-defective-geometry problem entirely (Q7, Q8).** AP-VLM never renders from any reconstructed model — it overlays a live, kinematically-projected grid onto the real-time RGB feed. This is a legitimate answer to "what is the render": *don't render from geometry at all, project markers onto the live camera image using extrinsic calibration.* It only works because of dense ArUco infrastructure and a **workspace-fixed** grid; it offers nothing for **object-fixed**, geometry-conditioned view menus (see below) — but it is real evidence that "annotate the live frame, don't synthesize a render" is a viable answer to Q7/Q8 when the marks are workspace/kinematics-anchored rather than object-surface-anchored.
- **Annotation (marks + coordinate text) measurably helps trajectory efficiency even when it doesn't move the headline SR (Q5).** `2DA` (annotated) vs `2DNA` (unannotated): identical SR on Scene 1 (1.0/1.0) but OSR 9 vs 0 and shorter successful-trial path length — and on Scene 2, `2DA` has notably lower PE (0.30 vs 0.44) and TLP (1.98 vs 2.33) despite equal SR (0.2). This is a hybrid image+text-label condition beating pure marks-only, i.e. evidence for the "annotate marks with explicit coordinate text" side of the text-vs-image question, at least for secondary (path-quality) metrics.
- **A real precedent of a monolithic seeing agent (not blind-orchestrator-plus-subagent) doing both sufficiency-judgment and next-view selection off the same annotated frame (RQ4, architecture-verdict question).** The closest prior art chose the "can see the render" design over a blind orchestrator dispatching to a separate vision subagent — worth weighing directly against Branch 1/RQ4's open question of whether the orchestrator should see.
- **Flat, non-hierarchical presentation works at this scale.** The full grid is projected/labeled every step (no collapse/expand, no query tool); only a simple "don't revisit" memory (`κ`) is layered on top. Supports the "our space is small enough to dump" hypothesis at the scale tested (tens of vertices), though the paper never states the actual vertex count shown per step, so this is suggestive, not quantified.
- **A concrete, if uncalibrated, stopping rule (Q13):** hard cap of 10 iterations + a VLM self-reported sufficiency judgment, no conformal calibration or numeric confidence threshold. Useful as a documented negative example — the closest prior art does *not* have a defensible "enough views" rule.
- **A genuine "no random/uniform baseline exists" data point (Q15).** The only baselines are `NAP` (single fixed home view) and, in the second experiment, TGCSR's 5 *fixed, hand-chosen* camera positions (front/back/sides/top) — never a random-viewpoint or random-walk baseline. Flag for Branch 2: this closest prior art cannot be cited as having ruled out "random active motion captures most of the gain."
- **OSR (Oracle Success Rate: success if the closest trajectory point to goal is within 0.1 m) is a usable metric candidate** to carry to Branch 2 alongside I-Perceive's View Coverage IoU and SeqVLM's projected-area score — it separates "got close but stopped/answered wrong" from "never got close," which is exactly the kind of diagnostic our benchmark needs.
- **Discrete vs. continuous vertex output (`3DD` vs `3DC`) shows no consistent winner** (Scene 1: 0.8 vs 0.9; Scene 2: 0.3 vs 0.2) at N=10 — this is a genuine (if underpowered) data point of *inconclusiveness* for the "indices vs. numeric coordinates" encoding question (Q4) rather than evidence for either side; do not over-read either direction from this table.

## What does NOT transfer, and why

- **The grid-construction mechanism is fundamentally workspace-anchored, not object/geometry-anchored** — it cannot answer RQ1/RQ2 (how to derive views from the object's PLY) at all; it is precisely the pattern our framing doc identifies as the problem, not a solution to it. Any claim that AP-VLM "does geometry-conditioned view planning" would be wrong — it does workspace-fixed grid navigation for occlusion resolution.
- **No point cloud, no mesh, no depth used anywhere** ("we did not use depth") — nothing here informs Q7's GraspView/SPAZER/VLM3D/SeqVLM sparsity-and-holes question, nor Branch 3's defective-survey-cloud handoff (Q18/MV-GEL). This paper simply never touches reconstructed geometry.
- **Feasibility of options is unhandled, not deliberately designed (Q11).** The paper's own limitations paragraph reports unreachable-workspace commands as an open failure, not a design choice among "silently remove / list as unavailable / affordance-score" — cite as a negative example (what happens when you don't handle this), not as an implementation of any of the three patterns.
- **No ordering/permutation experiment at all (Q10)** — grid vertices are presented by spatial projection position on the image, not as an explicit ordered menu; the paper never varies or discusses presentation order.
- **No hierarchical/collapse-expand or query-tool comparison (Q12)** — only the flat-dump condition is tested; there is no ablation against a query-based alternative to cite either for or against.
- **Exact prompt templates are absent from the paper** (confirmed by direct full-text read, not just a lossy fetch) — cannot resolve *how* GPT-4o was instructed to parse `(x;y)` labels or format output; treat any assumption about prompt structure as unsupported.
- **Ego/allocentric framing is not tested or discussed at all (Q1, Q2)** — no MMSI-Bench/ViewSpatial/SpinBench-style controlled probe of relating one viewpoint to another; the grid coordinates are presented in an absolute workspace/base frame, and whether the VLM reasons about them ego- or allocentrically is never examined, only outcome SR is reported.
- **Object set and task framing mismatch (Q16 test-case relevance is indirect):** aluminium tin, coffee mug, golf ball, strawberry, Lego block — containment/occlusion queries, not primitive-shape orthogonal-face defect inspection. Do not cite these specific numbers as evidence about box/cylinder orthogonal-view selection; only the *mechanism-level* failure modes (menu-confusion, discretization-granularity floor, unreachable commands, no random baseline) transfer.

## Answers / non-answers to branch questions

- **Directly useful for:** Q3/Q9 (measured, named compositional/menu-dimensionality penalty, `3Dx`→`3Dxy`), Q5 (annotated-marks-plus-text beats unannotated marks on path-quality metrics even at matched SR), Q7/Q8 (a real "don't render from geometry, project onto the live frame" answer — but only viable when marks are workspace/kinematics-anchored, not object-anchored), Q11 (negative example: unhandled infeasibility, cited in the paper's own limitations), Q12 (flat-dump precedent, no hierarchy tested), Q13 (uncalibrated stopping rule — hard cap + self-report, a documented gap), Q14 (this is itself a table-worthy entry: **ablated**, 8-way comparison, N=10/scene, **no variance reported** — flag accordingly), Q15 (no random/uniform baseline exists in this closest prior art — important gap for Branch 2), Q16 (three named, quotable failure modes: multi-axis menu confusion, fixed-granularity rotation missing the needed steep angle, unreachable-workspace commands), Q19 (OSR metric candidate), Q20 (real precedent for the "seeing" side of the architecture question — single agent, not blind-orchestrator-plus-subagent).
- **Explicitly non-answers, source elsewhere:** Q1/Q2 (no ego/allo probe of any kind), Q4 (discrete-vs-continuous ablation present but statistically inconclusive at N=10 — cannot resolve the Thinking-with-Novel-Views/MapGPT contradiction from this data), Q6 (no caption hand-off exists in this architecture — single seeing agent throughout, so nothing is destroyed/recoverable to analyze), Q10 (no ordering experiment), Q17 (no adjacency-graph structure attempted, positive or negative), Q18 (no point cloud used at all — cannot speak to MV-GEL's textureless-mesh finding).

## Bottom line

The closest published prior art confirms the field-level mechanism our project wants (VLM picks the next discrete viewpoint from a marked grid overlaid on an image, iteratively, zero-shot) is workable at small scale (SR up to 1.0 on an easy scene, dropping to 0.1–0.5 on a hard one), but it is built entirely on **workspace-fixed, geometry-blind** grid construction (no PLY, no depth, ArUco-anchored) — i.e. it instantiates rather than solves the exact flaw our framing doc names as the current system's core problem. Its most transferable content is three measured/quoted failure modes (menu-dimensionality confusion when a second rotation axis is offered, a fixed 35° rotation granularity that provably fails to reach a steep required viewing angle in Scene 3, and unhandled IK/workspace infeasibility), a real precedent for a single seeing agent instead of a blind-orchestrator-plus-vision-subagent split, and a clear absence: no random/uniform baseline, no variance reporting, no ego/allocentric probe, no ordering test, no hierarchical-vs-flat comparison, and no exact prompt text — each a concrete gap for Branch 2's benchmark and for later synthesis to not over-credit this paper for.
