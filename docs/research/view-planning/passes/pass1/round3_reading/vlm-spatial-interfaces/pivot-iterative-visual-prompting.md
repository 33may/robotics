## Core method / idea

The paper's founding insight, stated verbatim (§1, p.2): "although VLMs struggle to produce precise spatial outputs directly, they can readily select among a discrete set of coarse choices, and this in turn can be used to refine this set to provide more precise choices at the next iteration." This is exactly the sentence our branch cites PIVOT for.

**The visual prompt mapping (§3.1, Eq. 1):** Ω(I, a₁:ₘ) → (Î, w₁:ₘ) — a set of candidate actions a₁:ₘ ∈ A (a continuous action space, e.g. 3D Cartesian deltas) is projected via camera matrices onto image I, producing an annotated image Î and a set of textual labels w₁:ₘ (numbers) where wⱼ refers to the visual marker representing action aⱼ. This turns "emit a continuous action" into "select label j from a multiple-choice VQA question."

**The optimization problem (§3.2, Eq. 2):** find a ∈ A, w such that PVLM(w | Î, ℓ) is maximized, subject to (Î, w) = Ω(I, a). Solved iteratively (Algorithm 1, Fig. 2):
1. Sample a set of candidate actions a₁:ₘ^(i) from a distribution P_A^(i) (initialized as the full action space at i=0).
2. Project onto image + label: Ω(I, a₁:ₘ^(i)) → (Î^(i), w₁:ₘ^(i)).
3. Query the VLM via multiple-choice VQA: which labels are most promising for task ℓ.
4. Fit a new distribution P_A^(i+1) to the selected best actions (the paper approximates P_A as an **isotropic Gaussian**, §3.4).
5. Repeat until convergence or N iterations; return an action from the final best set.

This is explicitly framed as analogous to the cross-entropy method (§1, citing De Boer et al. 2005) — sample, evaluate, refit distribution, repeat, with the VLM playing the role of the evaluator instead of a simulator/reward function.

**Robustification via parallel calls (§3.3):** run E independent PIVOT instances in parallel from different random samples, then aggregate the E resulting candidates either by (a) fitting one new distribution across all E outputs, or (b) re-querying the VLM to pick the single best of the E. Purpose: mitigate the VLM landing in a local optimum from one bad initial sample.

**The literal annotation grammar (§3.4, our branch's specific target extraction):** actions are drawn as **arrows** emanating from the robot's current position (or image center if the embodiment isn't visible), each labeled with a **circled number at the arrowhead**. For depth (the third spatial dimension beyond the 2D image plane), **color and label/circle size jointly encode forward/backward motion**: e.g. in the manipulation setup, red arrows = move away from camera, blue = move toward camera; smaller circles = farther from camera (more forward), larger circles = closer to camera (more backward) — this exact color+size-for-depth convention is stated verbatim in the Direct-prompt text (Appendix H.4–H.5) and is the load-bearing detail our branch extraction note calls out. Gripper open/close is *not* drawn as a visual annotation at all — it's expressed purely in the text prompt, an explicit admission that not every action dimension is amenable to visual marking.

## Concrete results and numbers

**Navigation (Table 1, mobile manipulator, 4 tasks, real robot):** iteration and parallel calls both help, and together help most. E.g. "Go to the darker room": No-iter/no-parallel 25% → 3-iter/no-parallel 50% → no-iter/3-parallel 75% → 3-iter/3-parallel 100%. Not monotonic on every task ("Go to wooden bench": 3-iter/3-parallel is 50%, *worse* than 3-iter/no-parallel's 75%) — the paper does not flag or explain this regression, just reports the table.

**Manipulation (Table 2, mobile manipulator, 3 tasks):** "Pick coke can" reach/steps/grasp: 50%/4.5/0% (no-iter,no-parallel) → 67%/3.0/33% (3-iter) → 100%/3.0/67% (3-iter+3-parallel). Consistent monotone improvement here.

**RefCOCO zero-shot visual grounding (§4.3, Fig. 5):** GPT-4V + 3 rounds of PIVOT on 1000 examples from RefCOCO testA. "Strong performance even in the first iteration with modest improvement over further iterations" — exact accuracy/distance numbers are in Fig. 5 (bar/line chart, not a text table) but the qualitative claim (iteration 1 already strong, further iterations give diminishing returns) is explicit prose.

**Offline ablations, the numbers our branch cares about most:**
- **Text-vs-image encoding of identical spatial info (Table 4, navigation offline eval, L2 loss, lower better):** Image-annotation baseline beats a 3×3-grid-region text baseline (VLM asked to output "top left"/"bottom middle" etc.) on **every** task category: In-View 0.21±0.002 (image) vs. 0.26±0.15 (text); Semantic 0.23±0.012 vs. 0.35±0.14; Out-of-View 0.44±0.04 vs. 0.46±0.31. Text baseline has markedly higher variance in all three cases. This is a direct, ablated (not merely demonstrated) A-vs-B comparison — image annotation beats text description of the *same underlying spatial choice*, single VLM (GPT-4V), same task set, single-iteration comparison (no PIVOT iteration credited to either side).
- **Manipulation text-only baseline (Fig. 7b):** VLM selects among discrete language actions ("right"/"left"/"up"/"down") vs. full PIVOT visual arrows — "PIVOT outperforms text by a large margin" (exact bar values not in extracted table text, only in the figure).
- **Number of samples (Fig. 7a):** ablated at 5, 10, 20 samples per iteration. Finding: more samples → better *initial* (iteration-1) answer, but *worse* optimization over subsequent iterations, because a crowded image causes occlusion between nearby markers. 10 samples chosen as the practical sweet spot for "distributional coverage vs. visual clarity" — this is a stated, reasoned trade-off, not a swept-and-picked-max number.
- **Text prompt style (Fig. 13, Appendix D):** zero-shot CoT is the best performer (cosine similarity 0.48), few-shot direct is close (0.47) and "significantly more token efficient" (avg response length 368.27 chars for few-shot-direct vs. 1048.83 for zero-shot-CoT — nearly 3× fewer tokens for near-identical performance).
- **Prompt element ordering (Fig. 14, Appendix D):** preamble→image→task order gives 0.43 cosine similarity vs. 0.41 for image→preamble→task — "a small amount of variation... by a small margin," explicitly not a strong effect.
- **Iteration/parallel-call ablation (Fig. 6a, 7c, 7d):** increasing either alone helps; increasing both together helps most — consistent across navigation and manipulation offline evals, "echoes the findings in the online evaluations."

**Scaling (§4.5, Fig. 8):** across four Gemini model sizes (a–d, increasing params), PIVOT performance increases *monotonically* with model size on both manipulation and navigation offline metrics — direct evidence the method's ceiling is capability-bound, not prompt-bound.

**Visual annotation robustness study (Appendix G, Tables 6–7) — a second, distinct ablation, very relevant to our render-legibility question:**
- Table 6 (absolute arrow direction on a *blank background*, synthetic toy dataset, GPT-4V): accuracy is generally high (88–100%) across arrow color/thickness/head-size variants, but **direction matters a lot**: e.g. blue arrows pointing "down+right" only 17% correct vs. 100% for "up+right" with the same blue color — a large, unexplained direction-dependent asymmetry that is presented as raw data without an offered mechanism.
- Table 7 (object-referential arrow selection in a *realistic robot scene* — "which arrow points at object X"): accuracy collapses relative to Table 6 and varies enormously by object difficulty category: **Easy objects (plates, boxes, cubes) 0–100% depending on color; Very Hard objects (brushes, eccentric shapes) 0–44%.** E.g. red arrows: Easy 44%, Medium 100%, Hard 0%, Very Hard 0%. This is the paper's own quantified evidence that going from "classify an isolated arrow's direction" (near-ceiling) to "match an arrow to the object/geometry it's meant to indicate" (often near-floor for hard geometry) is where visual-prompt accuracy actually breaks down — directly relevant to whether numbered-arrow annotations will be legible on a defective/low-texture point-cloud render of a primitive shape.

**Franka real-robot results (Table 5, Appendix F, 7 tasks × 2 trials):** e.g. "Grasp the pepper shaker" XY/YZ/Steps: 50%/50%/8.0 (no-iter) → 0%/50%/– (3-iter, no parallel — *reach success actually drops to 0%*) → 0%/50%/– (3-iter+3-parallel). Average across all 7 tasks: XY 25%→28%→34%, YZ 38%→31%→59%, i.e. iteration/parallel calls do **not** uniformly help on this smaller task set — several individual tasks get *worse* XY reach with more iterations even as the average creeps up, driven by a couple of tasks (saltshaker, ketchup, can) improving a lot. The paper reports this table plainly without flagging the non-monotonicity — a caution against reading "more iterations/parallel calls always help" as a general law; it held cleanly only for the larger mobile-manipulator task set.

## Load-bearing assumptions

- **Depth/3D understanding is explicitly reported as broken, in the paper's own Limitations section (§4.6, verbatim):** "we examined expressing depth values as part of the annotations using colors and label sizes... we have observed that **none of the VLMs we tested are capable of reliably choosing actions based on depth**." This directly contradicts the impression our branch's round-2 map entry gives ("colour/size encoding forward-back depth" presented as the technique) — the technique is described, but the paper's own limitations section says it **does not reliably work**. Rotation is named as an even harder open problem: "generalizing to higher dimensional spaces such as rotation poses even additional challenges."
- **Actions are always projected via known camera matrices onto a live RGB (or RGB+depth-from-onboard-sensor) frame of a real scene** — never a rendered point cloud, never a partial/defective reconstruction. The visual prompt mapping Ω assumes a clean camera-to-image projection exists and that the resulting annotated image is a normal RGB photo a VLM would recognize from its training distribution.
- **The action space A being annotated is always continuous and low-dimensional** (2D navigation heading, 3D Cartesian deltas, 2D pixel pick/place) — never a discrete enumerated set of pre-computed, semantically distinct options (e.g. "view of face 1" vs. "view of face 2"). PIVOT's arrows are *directions from the current pose*, sampled densely and refined toward a continuous target; it is not solving "pick the best among 8 qualitatively different, already-fixed candidate poses." This is a structural mismatch with our problem that the branch entry's summary elides.
- **Rotational DOF is explicitly fixed/dropped, not solved (§4.1):** "although the end-effector has rotational degrees of freedoms, we fix these due to the difficulty of expressing them with visual prompting." The paper never attempts to have a VLM select among *orientation* options via visual annotation — only translational/positional choices. This bears directly on our "orthogonal to face" requirement, which is fundamentally an *orientation* selection problem, not a positional one.
- **GPT-4V / Gemini, zero-shot, no fine-tuning, no in-domain training data** throughout — the paper's stated purpose is to characterize current VLM limits, not to build a deployable system: "current performance is far from perfect... our aim is not necessarily to develop the best possible robotic control... but to study the limits and potentials."
- **The iterative refinement loop assumes the *correct answer is a single continuous point/region the sampling distribution can converge onto*** (isotropic Gaussian refit each iteration) — this is cross-entropy-method-style local optimization around one target, not enumeration/selection among a small fixed discrete menu of qualitatively different candidates (our actual problem: face 1 vs. face 2 vs. orbit-position-k, not "refine toward the exact best point near this approximate direction").

## What transfers to our setting

- **The core capability claim is directly load-bearing for us and is at least self-consistent across two independent ablations:** VLMs cannot reliably emit continuous/precise spatial values, but *can* select among a small number of coarse, visually-marked discrete options, and doing so via image annotation beats doing so via text description of the same underlying choice (Table 4: image beats text on every navigation subtask, with lower variance). This is real, ablated, first-party evidence for the family-B (seeing orchestrator, marked render) approach over family-A (blind orchestrator, text description) — for the *specific* sub-question of "point at/toward a location," not yet for "select among named discrete alternatives" (see below).
- **Numbered-circle/labeled-marker-at-endpoint is a directly reusable low-level annotation primitive** for drawing candidate views/directions on a render — this is the literal visual vocabulary (arrow + circled number label) our RQ4 (presenting the action space) would adopt if going the seeing-orchestrator route for view *selection framed as "pick a direction."*
- **Parallel-call aggregation (§3.3) is a cheap, demonstrated robustness technique** applicable to any single-shot VLM menu-selection call, independent of whether iterative refinement is used: run k independent selection calls, aggregate by re-querying or by voting. Directly reusable even if we don't adopt the continuous-refinement loop.
- **The visual-annotation-arrow robustness study (Appendix G, Tables 6–7) is a directly reusable experimental design**, not just a result: build a synthetic dataset varying annotation color/thickness/size, and separately test (a) raw direction-classification and (b) object/geometry-referential matching. This is exactly the protocol our benchmark (Branch 2) needs to test whether marks are legible on a point-cloud render before trusting any marked-render interface — cite as a template, and note its finding that referential accuracy on real/hard geometry is far below isolated-direction accuracy.
- **The token-efficiency finding (few-shot direct ≈ zero-shot CoT in accuracy, at ~1/3 the tokens, Fig. 13) is a reusable prompt-engineering data point** if we build a marked-render interface and care about latency/cost per view-selection call.
- **The explicit admission that gripper-close (a non-spatial/binary action dimension) is handled purely in text, not visually annotated**, is a useful precedent: not every decision needs to go through the visual channel — supports a hybrid (Family C) design where, e.g., "which primitive to inspect next" is text/menu-based while "which view of this primitive" is visually marked.

## What does NOT transfer, and why

- **Depth/3D encoding via color+size is asserted as the technique in our round-2 map's one-line summary, but the paper's own Limitations section reports it does not reliably work** — "none of the VLMs we tested are capable of reliably choosing actions based on depth" (§4.6, verbatim, quoted above). If we intend to encode viewpoint-distance-from-object or forward/back camera position via color/size on a marked render, PIVOT's own authors report this specific encoding failed for them. This is a negative finding our branch's extraction should surface as a caution, not just cite the technique's existence.
- **Rotation/orientation selection is never attempted — explicitly dropped as too hard to express visually (§4.1).** Our core requirement (evidence views orthogonal to a surface) is fundamentally about camera *orientation*, the one DOF class PIVOT explicitly excludes rather than solves. PIVOT is evidence for "VLMs can pick a rough direction/position via visual marks," not evidence for "VLMs can pick a rough orientation/angle via visual marks" — that generalization is unproven here and the paper flags it as an open, harder problem.
- **PIVOT's action space is continuous and refined toward one target via CEM-style resampling — it never demonstrates selecting among a small number of already-fixed, qualitatively distinct discrete alternatives** (e.g. "orbit position around a cylinder" vs. "face of a box" vs. "another face of the same box"). Our RQ3/RQ4 problem (address and select among a geometry-derived discrete menu with semantic structure — face 1 vs. face 2, adjacency, etc.) is a different task shape than "converge a Gaussian onto the single best nearby point." The paper's iterative-refinement mechanism (resampling densely around promising candidates) does not obviously apply to a menu of already-final, non-refinable discrete options; only the *first-iteration multiple-choice-selection* step is structurally analogous to our problem, not the refinement loop.
- **Every experiment operates on a live RGB (or RGB+onboard-depth) camera image of a real, textured scene** — nothing here speaks to legibility of marks on a rendered, partial, defective, possibly colorless point cloud (our actual render source per the framing doc's ~4cm fused-vs-single-view offset and glossy-surface dropout constraints). Appendix G's referential-arrow-accuracy collapse on "Hard"/"Very Hard" objects (down to 0% for some colors) is the closest available signal, and it is a *negative* one for how well marks survive difficult/ambiguous geometry — worth treating as a lower bound risk, not evidence marks will work on our render type.
- **No discussion whatsoever of viewpoint selection, camera-pose choice, or "which of these candidate photos should I look from"** — PIVOT annotates actions/waypoints *within* a single given image, never chooses among multiple candidate *camera poses/renders*. It is not a Family-B "contact sheet of candidate views" system (contrast with Manipulate-Anything, GraspView, SPAZER in our own round-2 map) — it is a "mark up this one image to select a point/direction" system. The paper is silent on the chicken-and-egg problem (who chooses the render viewpoint) that several of our other Family-B candidates address directly.
- **Non-monotonic robustness results (Franka Table 5, wooden-bench task in Table 1) show iteration/parallel-calls do not uniformly help** — on smaller task sets/fewer trials, more iteration or more parallel calls sometimes *degrades* individual-task success even while the average improves. Any claim that "just add more PIVOT iterations" is a free robustness knob should be qualified by this.
- **All quantitative ablations are run on 2D navigation/pixel-pointing and 3D-position manipulation tasks with small sample counts (10–60 offline examples, 2–5 trials per real-robot task)** — none of the reported numbers come from tasks resembling ours (discrete geometric-primitive view selection); treat every number here as evidence about the *general encoding principle* (image beats text, marks are learnable, depth-via-color fails), not as a performance estimate transferable to our task.
