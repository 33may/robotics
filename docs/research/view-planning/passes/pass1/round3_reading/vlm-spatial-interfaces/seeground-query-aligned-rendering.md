## Core method / idea

SeeGround is a **training-free, zero-shot 3D visual grounding (3DVG) pipeline**: given a 3D scene point cloud and a natural-language referring expression, output the 3D bounding box of the one target object the expression describes (Eq. 1: `bbox = 3DVG(S, Q)`). It works entirely through 2D-VLM calls over a **hybrid representation** — one query-aligned rendered image plus a text-based spatial description — with no 3D-specific training. Four ingredients:

1. **Object Lookup Table (OLT, Eq. 2):** an off-the-shelf open-vocab 3D detector runs once per scene, producing `{(bbox, sem)}` for all N objects. This is the *text-based 3D spatial description* channel — exact positions/dimensions/labels, computed once and reused across every query on that scene (§3.1).
2. **Perspective Adaptation Module (PAM, §3.2, Eqs. 4–5, 8–13):** a **text-only** VLM call reads the query `Q` (with few-shot example prompts `E^(E)`, no image) and outputs an anchor object `A` and candidate target objects `O^(C)` (Eq. 4). If no anchor is identifiable (e.g., query about "the chair" among several chairs with no other referenced object), a placeholder anchor is substituted — the target itself, or the centroid of multiple targets if several targets are named. **The camera pose is then computed by a fixed geometric rule, not searched or scored:** start at scene center, look at `A`, then move the eye point backward and upward away from `A` to widen the field of view (§3.2, prose only — no explicit formula for the backward/upward offset magnitude is given in the paper). `look_at_view_transform` (Pytorch3D's standard function, listed in §10 Public Resources) then derives `R_c, T_c` from eye position `e`, look-at target `at`, and an `up` vector via the standard forward/right/up construction (Eqs. 8–11: `z_axis = normalize(at−e)`, `x_axis = normalize(up×z_axis)`, `y_axis = z_axis×x_axis`, `R_c=[x_axis,y_axis,z_axis]^T`, `T_c=e`). One point cloud render results: `I = Render(S, R_c, T_c)` (Eq. 5/13).
3. **Fusion Alignment Module (FAM, §3.3, Eqs. 6, 14–17):** to stop the VLM from losing the text↔image correspondence (e.g., "which of these five chairs in the image is 'the chair with the floral pattern' from the text?"), every OLT object's 3D points are projected into the rendered view via the same `R_c, T_c` (Eq. 14). **Depth-aware visibility filtering** resolves projection occlusion with a hard z-buffer test: a scene depth map `D(p′) = min_{p_s∈S} d_s` is built (Eq. 15); a projected point is `Visible(p)=1` iff its own depth `d_p < D(p′)` (Eq. 16, strict inequality — ties/near-ties go to "occluded"); an object is `Visible(o)=1` iff the count of its visible points `≥ α·|P_o|` for a threshold factor `α` (Eq. 17) — **`α`'s numeric value is never given in the paper body**, only introduced symbolically. Visible objects get a point-marker `M_o` placed at the centroid of *only their visible points* (not all points), composited onto the image (Eq. 6: `I_m = I⊙(1−1_visible) + M_o⊙1_visible`).
4. **Object prediction (Eq. 7):** the query `Q`, marked image `I_m`, and text description `T` are given together to the 2D-VLM, which reads the marker IDs (via OCR — an explicit, load-bearing requirement, §7.1) off the image and outputs a predicted object ID resolved back to a 3D bbox via the OLT.

Main-experiment VLM: **Qwen2-VL-72B** (open-source, chosen for cost/reproducibility over GPT-4).

## Concrete results and numbers

**Headline (Abstract, §4.2):** ScanRefer val: Acc@0.25/0.5 Overall = 44.1/39.4 (Table 1); prior zero-shot SOTA ZSVG3D = 36.4/32.7 → **+7.7pp is the Acc@0.25 delta specifically** (44.1−36.4), not Acc@0.5 (which is +6.7pp, 39.4−32.7) — the abstract's single "+7.7%" figure is Acc@0.25 only; check which threshold matters before quoting this number elsewhere. Nr3D val (Table 2): SeeGround Overall = 46.1 vs. ZSVG3D 39.0 → **+7.1pp absolute**, restated in §4.2 prose as **"18.2% improvement"** — that 18.2% is the *relative* gain (7.1/39.0), not a second absolute delta; the two numbers describe the same 7.1pp gap in different units. Ground-truth-proposal upper bound (Table 10, ScanRefer): with GT 3D boxes instead of a detector, SeeGround reaches **59.5%** vs. 44.1% with Mask3D — i.e., ~15pp of end-to-end error traces to upstream detection, and even with a perfect detector, **40.5% of queries still fail** — a hard ceiling on the VLM-reasoning half of the pipeline that GT proposals cannot buy out.

**Table 9 — visual prompt type ablation (Nr3D, 40 of 130 val rooms only, not the full val set):** Marker 47.7 overall (best on Hard/Indep/Overall) vs. Contour 47.5 (best on Easy/Dep, essentially tied with Marker) vs. BBOX 45.1 vs. Mask 45.0 (worst two). Authors' stated reason (§7.2): bbox/mask overlays occlude the color/texture cues the VLM needs for disambiguation, and duplicate spatial information already present in the text channel, actively costing accuracy rather than being neutral.

**Table 10 — 3D detector ablation (ScanRefer):** Mask3D 44.1, OVIR-3D 30.7, GT 59.5, vs. ZSVG3D's Mask3D 36.4 / OVIR-3D 19.3 — SeeGround's margin over ZSVG3D widens with a weaker detector (44.1−36.4=7.7pp with Mask3D vs. 30.7−19.3=11.4pp with OVIR-3D), suggesting SeeGround's visual grounding is somewhat more robust to noisy upstream proposals than ZSVG3D's purely-programmatic (center-projection + hand-coded spatial-relation functions) approach — plausible mechanism: SeeGround can use visual context to recover from a bad/missing detection (§4.3 "Robustness Evaluation," Fig. 7, **qualitative case study only, one example, no quantified accuracy delta** — the model correctly finds "the cabinet" when the anchors "printers" and "counter" are dropped from the text, by reading the image instead).

**Table 8 — VLM scale ablation (Nr3D):** Qwen2-VL-7B 33.3, InternVL2-8B 34.3, InternVL2-26B 38.0, Qwen2-VL-72B 46.1. The 7B→72B gap within the same model family is **12.8pp** — a same-pipeline, same-encoding demonstration that spatial/viewpoint grounding accuracy scales steeply with VLM size; the 7–8B tier sits ~12pp below the 72B tier under an *identical* hybrid encoding, meaning the encoding alone does not rescue small-model spatial reasoning.

**Fig. 8 / §4.3 "Type-Wise Error Analysis" (185 manually reviewed samples, 10 rooms):** four error categories — Relation, Classification, Viewpoint, Localization. Only one number is stated in prose and independently checkable from the extracted text: **SeeGround's error rate on spatial-relationship queries is 19%**, described as still "high" despite the visual grounding improvements, with an explicit authors' admission: *"Current viewpoint selection strategies also fall short in handling complex scenarios like 'when the window is on the left' or 'upon entering from the door'."* The full per-category bar-chart breakdown (Fig. 8) was **not visually inspected**; only the 19% figure and the viewpoint-limitation sentence are citable from text.

## Load-bearing assumptions

- **Task shape is referring-expression disambiguation among already-detected objects, not next-view selection for an ongoing inspection.** The "view" in SeeGround is a *means* to help a VLM read text-labelled markers correctly; the deliverable is an object ID resolved to an already-known 3D bbox, not a camera pose or an inspection image. There is no analog to "is this the best evidence view of surface region X" anywhere in the paper.
- **Exactly one render per query, computed once by formula, never revisited.** No iteration, no candidate-view menu, no scoring loop, no stopping criterion, no multi-view fusion. The VLM never sees more than one image per query and is never asked to choose among viewpoints — it only ever *reads* the one it's given.
- **The viewpoint objective is "wide, uncluttered context around a semantically identified anchor," which is the opposite goal from surface-orthogonal inspection.** PAM's stated rule ("move backward and upward from the anchor to gradually cover a broader view," §3.2) explicitly optimizes for scene coverage/context, not for incidence angle or surface-normal alignment. **The paper contains zero mentions of orthogonality, incidence angle, or surface-normal alignment anywhere** — not a competing formulation of "best view," just a different question entirely.
- **Anchor identification is text-only and precedes any rendering** (Eq. 4: `VLM(Q, E^(E))`, no image argument). The camera pose is then a closed-form function of the anchor's already-known 3D position (from the OLT) — no image-based iteration or search ever informs *where* to look; only the *content* of the one resulting image is used by the (separate) grounding VLM call.
- **Point clouds are ScanNet RGB-D room scans** — dense, textured, walled/floored, from real furniture-scale indoor environments with a functioning detector pipeline (Mask3D/OVIR-3D) built for this domain. Not survey point clouds of single small objects; no per-view depth dropout, no glossy-surface behavior, no fused-vs-single-view offset is discussed anywhere, because the domain doesn't have that failure mode in the same way tabletop inspection does.
- **No IK/reachability/collision constraints.** The "camera" is a virtual re-render (Pytorch3D) of an existing static point cloud — there is no robot, no physical motion, no notion of an unreachable viewpoint.
- **`α` (the visibility fraction threshold, Eq. 17) is left unspecified numerically** in the paper — a load-bearing hyperparameter of the depth-aware marker-placement scheme that isn't given a citable value in the text (would need the code repo, not fetched here).
- **Zero variance/confidence-interval reporting anywhere in the paper.** Every ablation table (3, 4, 8, 9, 10) reports single numbers with no seeds, no repeated trials, no error bars, no significance test — including the Table 4 view-selection ablation this document was selected for.

## What transfers to our setting

- **A clean, ablated (Table 3, not merely demonstrated) example of hybrid text+render outperforming either channel alone, with the mechanism identified**: the gain is concentrated in *explicit cross-modal binding* (FAM's marker↔text-ID correspondence, +3.6–3.8pp) rather than in simply having more raw visual channels present (layout/texture alone add only ~2pp) — directly answers the branch's "extract the conditions, not the verdict" instruction for the text-vs-image question: **the condition under which the render helps is when there's an explicit, checkable identity link between what's marked in the image and what's named in the text — an unlinked image or unlinked text underperforms a linked combination of either.**
- **A citable case where a correctly-chosen render substitutes for explicit metric-coordinate text**, not just supplements it: Table 3(e) vs (d), dropping raw 3D-position text but adding PAM still nets +1.7pp. Weak but real evidence against "always give the model precise coordinates" as a universal rule — worth flagging to the numerical-pose-encoding branch question, though this is a component ablation, not a controlled coordinate-precision sweep, so it only shows *substitutability*, not that coordinates actively hurt (contrast with MapGPT's stronger claim, not verified here).
- **A concrete, cheap, "blind-decide-where / seeing-decide-what" architectural pattern that already works at this task's scale**: the anchor (hence the render's viewpoint) is picked by a **text-only** VLM call before any image exists (Eq. 4); a separate VLM call, given the resulting image, does the actual grounding. This is direct empirical support (Table 3(e)/(f) show PAM helps; Table 4 shows the query-aligned rule beats four alternatives) for splitting "where to look" from "what do I see" into two calls, one blind and one seeing — the core shape of our current blind-orchestrator-plus-vision-subagent design. **Important limit on this transfer**: SeeGround's "where to look" decision is a single deterministic geometric formula conditioned on one anchor point, not a discrete menu the blind stage must reason over or navigate — it answers "can a blind stage usefully pick a viewpoint anchor from text alone," not "can a blind stage navigate a structured space of candidate views." The chicken-and-egg problem (branch Q8) is resolved here by **not** having any stage browse candidate renders at all — reducing it to a closed-form geometry lookup keyed off a text-identified 3D point.
- **A validated design rule for visual marker choice**: point/center markers ≥ contour, both clearly beat bounding-box/mask overlays (Table 9, though only on a 40/130-room subset), because region-overlays occlude the appearance cues the model needs and duplicate information already carried by the text channel. Transferable heuristic for our own view-marking/labelling design if we ever overlay IDs on rendered views: **don't let a visual prompt re-encode information the text channel already carries; let it carry only the information the text can't (identity/binding).**
- **An explicit, first-class failure mode to hand to Branch 2's test-case catalogue**: OCR/ID-marker dependence (the pipeline requires a VLM with working OCR to read in-image object-ID labels, §7.1) and viewpoint-dependent relational-language failures even in the best configuration (19% relation-error rate persists, "when the window is on the left" scenarios explicitly named as unsolved, §4.3) — both are authors' own named limitations, not our inference.
- **A capability-floor data point**: same encoding, same task, 7–8B VLMs score 12.8pp below the 72B model (Table 8) — a same-pipeline scaling curve corroborating (not proving on its own) the branch's general concern that spatial/relational grounding is capability-gated by model scale.

## What does NOT transfer, and why

- **No discrete, navigable action space of views is ever presented to a VLM.** SeeGround never asks a model to pick among named/indexed viewpoints, never has adjacency or "opposite face" relations, never loops. RQ3/RQ4's central problem (present a geometry-adaptive space so a model can navigate it) has **no analog** here — the closest thing, Table 4, is an *offline researcher-side* ablation over five fixed camera-placement formulas, not an online model-facing choice.
- **No orthogonality/incidence-angle objective, and no evidence bearing on it.** PAM's viewpoint goal (broad context around an anchor) is not a stand-in for "camera normal to a surface" — nothing here informs RQ1/RQ2's view-quality scoring, and nothing here should be read as evidence about orthogonal-view selection specifically, despite superficially being "the" query-aligned-viewpoint paper.
- **No defective/sparse/holed geometry, no ~4cm fused-vs-single-view offset, no glossy dropout.** §7.4 and §9.2 *acknowledge* rendering-quality risk in the abstract ("low-quality point clouds… can compromise alignment," §9.2; domain gap between rendered and real images, citing EmbodiedScan, §7.4) but this is **argued, not measured** — no ablation perturbs point-cloud completeness or introduces holes/dropout and reports a resulting accuracy delta. The paper's own depth-aware visibility test (Eqs. 15–17) is a hard z-buffer occlusion test that assumes a basically complete, correctly-registered cloud; it has no way to distinguish "correctly occluded by another object" from "missing because the sensor never saw it" — exactly the ambiguity our fused-PLY holes would introduce, and the paper never confronts this because ScanNet clouds don't fail that way. **Direct negative answer to the branch's sparsity/holes/glossy-dropout question: this paper does nothing about it.**
- **No IK/reachability/collision-infeasible-view handling of any kind** — irrelevant to the branch's "how should infeasible views appear" question; there is no robot and no physical constraint in this pipeline.
- **No stopping-criterion, no hierarchical/on-demand exposure, no option-count/ordering study.** Single render, single VLM call, done — none of the "how many views," "does order matter," "on-demand vs. dump" branch questions have any evidence source here.
- **The two static-baseline-family results (Table 4's Center/Edge/Corner-to-X and BEV) are room-scale scene-composition heuristics** (camera positioned relative to two named points, or straight overhead) that don't correspond to anything in a tabletop single-object regime — the specific accuracy numbers (40–43% band) are not transferable magnitudes, only the qualitative ranking (query-aligned > BEV > the three point-to-point heuristics, with the largest gap on viewpoint-dependent language) is potentially informative, and even that should be treated as one data point from one task family, not a general law.
- **No handling of textureless/colorless geometry** (branch's MV-GEL handoff concern) — ScanNet scenes are textured, colored real-room scans; nothing here speaks to whether view-quality reasoning survives on bare/defective survey geometry.

## Answers mapped to specific branch questions

- **Selection-reason claim, verified**: "Query-aligned viewpoints beat static cameras most on directional queries" — confirmed via Table 4: the margin over the best static baseline (BEV) is largest on View-Dependent (+5.4pp table-computed, +5.7pp per prose — discrepancy noted above) and Hard (+4.4pp) columns, smallest on Easy (+1.1pp) and View-Independent (+1.4pp). This is Nr3D's own "View-Dependent" annotation, i.e., queries requiring adoption of a specified observer viewpoint — the paper's closest operational proxy for what the branch calls "directional."
- **Q re: chicken-and-egg (Branch handoff)** — SeeGround's answer: don't browse candidate renders; run one **text-only** VLM call to pick a semantic anchor point (Eq. 4), then compute the render viewpoint from that anchor by closed-form geometry (§3.2, Eqs. 8–13). No render-then-pick loop exists. Cost: this only works because the "right" viewpoint is well-approximated by a single generic heuristic (back away and up from whatever matters); it would not obviously generalize to our setting where the "right" viewpoint must be surface-orthogonal to a specific, shape-dependent face — a fixed backward/upward offset rule has no notion of surface normal to align to.
- **Q re: text vs. image trade-off, conditions not verdict** — Table 3 gives the conditions: raw text-only channels underperform (37.7–39.7%); adding an *unlinked* image channel alone is not tested in isolation (their minimum image-inclusive rows already have FAM); the isolatable finding is that **explicit binding (FAM) is what converts "text + image both present" into a large gain**, and a well-aimed image can (row e) outperform raw coordinate text used without that image.
- **Q re: numerical pose encoding (Thinking-with-Novel-Views vs. MapGPT contradiction)** — SeeGround offers a data point on the MapGPT side (image can substitute for precise coordinate text, Table 3d vs. e) but this is a component-presence ablation, not a controlled sweep of coordinate precision/format, so it does not directly adjudicate that specific contradiction — flag as weak, indirect evidence only.
- **Q re: marker/encoding of camera pose or object ID** — Table 9: minimal point markers beat mask/bbox because region-overlays occlude appearance cues and duplicate the text channel's spatial info; contour ties with marker. Directly reusable design guidance, caveated by the 40/130-room subset size.
- **Q re: named failure-mode catalogue for Branch 2** — OCR/marker-ID dependence (hard requirement, §7.1); persistent 19% spatial-relation error rate even in the best configuration (§4.3); explicit authors' admission that viewpoint-dependent phrases like "when the window is on the left" remain unsolved (§4.3); GT-proposal ceiling of 59.5% showing ~40% of queries fail even with perfect object detection, i.e., a real VLM spatial-reasoning ceiling independent of upstream noise (Table 10).
- **Q re: evidence discipline table** — see the per-table breakdown above (Tables 3, 4, 8, 9, 10 are ablated with deltas but **zero variance reported anywhere**; §7.4's rendering-fidelity claim and §9.2's limitations are argued/demonstrated only, not ablated — flag accordingly, do not cite §7.4/§9.2 as measured evidence).
- **Q re: architecture verdict (parallel/read-heavy orchestrator-worker vs. tightly-interdependent single-agent, and does the answer change if the orchestrator can see)** — SeeGround is empirical support for a **blind decision (anchor pick, text-only) feeding a seeing decision (grounding, image-based)** working well at this task's scale (Tables 3, 4), but it is evidence for the *simplest* version of that split — one blind decision, one fixed formula, one seeing call, no loop — and says nothing about whether a blind orchestrator can successfully navigate a larger, structured, multi-option action space (our actual RQ4 problem). Treat as supportive precedent for the *pattern*, not evidence that the pattern scales to our harder navigation problem.
