# E3VS-Bench: A Benchmark for Viewpoint-Dependent Active Perception in 3D Gaussian Splatting Scenes

- **arXiv**: 2604.17969v3 [cs.CV], v1 submitted 20 Apr 2026, v3 29 Jun 2026
- **Authors**: Koya Sakamoto, Taiki Miyanishi, Daichi Azuma, Shuhei Kurita, Shu Morikuni, Naoya Chiba, Motoaki Kawanabe, Yusuke Iwasawa, Yutaka Matsuo
- **Source used**: full HTML (`arxiv.org/html/2604.17969v3`), fetched and parsed directly across three targeted passes (abstract, main methodology/results, then a focused pass on judge controls / stats / geometry-defect content). Section/table numbers below are as in the paper.
- **Code/data**: "The benchmark, code, and dataset are publicly available at https://k0uya.github.io/e3vs-proj/" (abstract). Project page not independently crawled in this pass.

## Core idea (§1, §3.1–3.2)

E3VS-Bench is an embodied 3D visual-search benchmark: an agent controls a camera in full **5-DoF** (3D translation + yaw + pitch) inside photorealistic **3D Gaussian Splatting (3DGS)** reconstructions of real scenes, and must answer a question that — by construction — cannot be answered from the agent's starting view or from prior knowledge alone. The paper's headline complaint about prior EQA/active-perception benchmarks: "most existing EQA settings... treat the agent as a 2D moving camera restricted to planar navigation... do not evaluate the fine-grained viewpoint control required to reveal task-relevant visual details" (Introduction). 3DGS is chosen specifically because it "preserves fine-grained visual details (e.g., small text and subtle attributes) often degraded in mesh-based simulators" — i.e. the representation is picked to make single-view *disambiguation* (not coverage/reconstruction) the thing under test.

This is a fundamentally different object than ObjView-Bench or the classical NBV literature: there is no reconstruction target, no GT mesh, no coverage metric. The "evidence" being sought is *semantic* (does this viewpoint resolve an ambiguous attribute/relation/count), not *geometric* (does this viewpoint complete a point cloud). Keep this framing distinction in mind throughout — it explains most of the "does not transfer" section below.

## Dataset & episode construction (§3.2, §5.1, Fig. 2, Table 1)

- **99 3DGS scenes** (from an original 105 curated pool) sourced from **SceneSplat++**.
- **2,014 question-driven episodes** derived from **1,290 unique QA pairs**.
- Splits: **Train** 1,406 episodes / 900 QA pairs / 68 scenes; **Val** 231 / 132 / 10 scenes; **Test** 377 / 258 / 21 scenes (§5.1).
- Six question categories (Fig. 5): Object Search, Object State, Object Attribute, Context-Guided Search, Spatial Reasoning, Counting.
- **Five-stage construction pipeline** (Fig. 2):
  1. Scene curation from SceneSplat++.
  2. QA generation via VLM (Gemini 2.5 Flash): multi-view rendering at distances chosen so the target object spans ~3/5 of image width/height; VLM filters occluded/ambiguous views; generates candidate questions over "intrinsic attributes (color, material, branding) and extrinsic spatial relations."
  3. Invalid-QA filtering: **~1,120 human-annotation hours** removing ambiguous, multi-interpretable, or objectively unanswerable questions.
  4. Viewpoint labeling: "expert annotators select viewpoints that contain sufficient information to answer" each retained question (§3.2) — a **set** of answerable viewpoints 𝒱_ans, not a single canonical point; physically invalid (geometry-penetrating) viewpoints removed. No statistic on |𝒱_ans| (average set size) is reported anywhere in the paper — a real gap if you wanted to reuse this as a template for how large a GT-view equivalence set should be.
  5. **Answerability filtering** (the "unanswerable from a single view" step — see below).

## The "unanswerable from a single view" construction algorithm (§3.2) — the design principle we're here for

A QA pair survives into the benchmark only if a VLM-as-judge (GPT-5.1) scores it **<3/5 in BOTH**:
- **Blind setting** — no visual input at all, judged on prior knowledge only, and
- **Initial-viewpoint setting** — single static image from the episode's start pose v₀.

Exact quote: "QA pairs scoring 3 or above in either setting are excluded, where the threshold is chosen as midpoint of 1–5 scale to conservatively filter out cases showing any indication of being answerable without active exploration" (§3.2). Consequence, stated directly: "Remaining episodes cannot be solved from prior knowledge or initial observation alone, and require active 5-DoF viewpoint transitions and information gathering for accurate answers."

This is a **two-gate rejection filter**, not a generative construction rule — it doesn't synthesize hard questions, it discards easy ones post-hoc using the same judge model that later scores the benchmark itself (see Q3/circularity below). The mechanism is directly portable to our setting as a *validation check*, not as GT: for each candidate inspection question/task, verify it cannot be resolved from the current default/uniform-sphere view (or from a non-orthogonal view) — if it can, the task doesn't actually test view selection and should be dropped from the benchmark. The dual gate (no-vision AND single-fixed-view) matters: a defect-visibility task could be "unanswerable blind" trivially (blind is always unanswerable for any visual question) but still answerable from the default view, so the binding gate for us is the second one.

## Evaluation protocol & metrics (§3.1, §5.1)

- **Unit of evaluation = (scene, question) episode**, scored end-to-end by a single holistic number. There is no per-region or per-(object,surface) scoring anywhere in the paper — directly maps onto our Q1's second, non-selected option: "(object, question) episode scored end-to-end."
- **Primary metric — VLM-as-judge score**: S = J(O_T, q, ŷ, y, O_goal) ∈ {1,...,5}, where the judge (GPT-5.1) receives the agent's final observation O_T, the question q, the predicted answer ŷ, the ground-truth answer y, and the human-annotated goal image O_goal (§3.1). 5 = perfectly correct, 1 = entirely incorrect. This is the load-bearing design move the paper description flagged: **the GT goal view is fed to the judge for scoring, never to the agent** — the agent must find evidence on its own; the goal image only lets the judge verify the final observation actually supports the answer, and (per Appendix 0.E) handle valid-but-unannotated alternative viewpoints by reference comparison.
- **Secondary metrics**: Navigation Steps (mean episode length, cap 25 steps), Collision Rate (binary, 1 if any collision occurred during the episode).
- **Episode horizon**: max 25 steps, "providing sufficient exploration budget" (§5.1) — a small-fixed-ish budget with a hard cap, no explicit auto-stop criterion beyond the model's own `stop` action (part of the discrete action set below).
- **Rendering**: 512×512 px, 90° FOV.

## 5-DoF viewpoint action space (§3.1, Appendix 0.D)

- State v_t = (x_t, y_t, z_t, θ_t, φ_t) ∈ ℝ⁵ — 3D Cartesian position + yaw + pitch (no roll).
- **Discrete action set**: translation {move_forward, move_backward, move_left, move_right, move_up, move_down} at **0.25 m/step**; rotation {turn_left, turn_right, look_up, look_down} at **30°/step**; plus a `stop` action.
- Forward/backward move along the *camera's* view direction (camera-frame axis) — "meaning agent moves up/down if camera tilted" (Appendix 0.D), i.e. translation is coupled to current gaze, not world-frame.
- Collision handling: "Collision after executing action leaves state unchanged" (§3.1) — a no-op rather than an episode-ending failure (contrast: our IK/collision-reachability constraint, which excludes a view from the action space outright rather than letting the agent bump into it and stay put).
- **Action-frequency finding** (Fig. 4c, §3.3): move_backward is used more than move_forward, move_up is the most-used single action, and look_down more than look_up — interpreted as "gaining context by moving away from target is often necessary." This is a concrete empirical signal that "get farther away / look down" is a common corrective move even when the naive intuition is "get closer" — worth a flag for our own action-space design, though it's about *semantic disambiguation distance*, not *orthogonality to a surface*, so it doesn't directly validate anything about our sphere-vs-face-normal question.

Both the discrete quantized action space (fixed step sizes, small finite move/turn set) and the collision-as-no-op handling are directly comparable design points to our own action-space discretization decisions (framing doc RQ3/RQ4, Constraints) — a working precedent for how one system made viewpoint selection tractable for a VLM without emitting metric poses (their agent never emits a pose either — it emits one of ~11 named discrete actions per step, closer to steering a plan through a graph than to picking a target view directly). Note this is *closer to a keyboard/incremental control scheme* than to our *pick a labeled discrete view from a pre-enumerated set* scheme — the two "discrete action space" designs are not the same shape, and that difference matters for RQ4 (presenting the space to the VLM): E3VS-Bench sidesteps the "how do I describe N labeled viewpoints to the model" problem entirely by making the action space small, fixed, and orientation-relative regardless of scene geometry.

Per-category human scores range 3.12 (Object Search) to 4.06 (Object Attribute, Context-Guided Search); every model trails human on every category (§6). The **best model (Gemini 3.0 Flash, 2.79) still trails human (3.53) by 0.74/5** — a substantial, explicitly reported gap, and this is the paper's headline finding.

**Static baselines (Table 3)** — isolating how much the *active* part of active perception matters:
- Blind VLM: 1.82; VQA-at-start (single frame, v₀): 2.14; VQA-at-birdview: 1.48 (worse than start — a fixed "helpful-looking" overview viewpoint is not actually informative); **VQA-at-goal: 3.58** (i.e. giving the model the human-labeled GT goal view directly nearly matches human performance, 3.58 vs 3.53) — this is the clean ceiling check: the bottleneck is viewpoint *selection*, not answering given the right view. 2D visual-search baselines (SEAL/DyFo, adapted from flat-image active search) score 1.68–1.86, i.e. barely above blind — confirming that 2D active-search machinery does not transfer to 5-DoF embodied search.

**Table 4 — ablations**: reasoning budget helps GPT-5.1 (2.42→2.70 with medium thinking effort, fewer steps too: 15.04→13.78) but Gemini 3.0 Flash is "little sensitive to reasoning budget" (§5.3) — a model-specific effect, not a general one. Multi-frame memory (3–5 frames) doesn't move judge scores but does reduce navigation steps and collision rate (Fig. 6) — cheaper/safer paths to the same answer quality, not better answers.

**Table 5 — goal-view initialization**: starting the agent already at (or with) a sufficient-evidence viewpoint roughly halves steps and lifts scores substantially (Gemini 3.0 Flash: 2.79→3.41 at 11.29→6.60 steps; Qwen3-VL-8B: 2.46→3.38 at 18.73→12.06 steps) — a strong signal that most of the score deficit is attributable to *finding* the right view, not reasoning over it once found, once you control for starting position.

**Failure-mode breakdown (§5.2)**: Counting (CNT) is called out as a category with a stated structural limitation — "counting requires accumulating evidence across 5-DoF trajectory, which single-observation EQA approaches cannot handle" — and Object Attribute (OA) is "highly sensitive to viewpoint selection and requires both exploratory viewpoint discovery and detailed visual recognition" (§5.2).

## Judge protocol & its controls (§3.1, §3.2, §5.1, Limitations §6) — thin, and the paper says so itself

- **Single judge, no anonymization, no position swapping, no multi-judge consensus, no held-out human-labeled validation slice beyond an aggregate correlation check.** The construction-time filter (§3.2) and the evaluation-time scorer (§5.1) both use closely related judge setups (GPT-5.1 as VLM-judge), i.e. the same model family gates *what counts as a valid question* and *how episodes are scored* — a two-stage but not independently-sourced judge design.
- **Judge validity check**: "Spearman correlation ρ=0.54 with human evaluation," described by the authors as "reasonable agreement" (§5.1) — 0.54 is a moderate, not strong, correlation; worth treating as a caution rather than a validated-judge claim.
- **Author-stated limitation, verbatim** (§6): "In some cases, agent's final observation differs substantially from human-annotated goal viewpoint while receiving similar judge score, indicating automated evaluation may insufficiently capture viewpoint adequacy." This is a direct, self-reported instance of exactly the Q15 failure mode (wrong-view/right-answer or right-view/mis-scored) — the paper both exhibits the problem and names it, without building a view-correct × answer-correct grid to separate it out. It's evidence *for* building that grid (Q15), demonstrated by its absence causing a diagnosed but unquantified error mode here.
- **Self-preference data point**: GPT-5.1 is both a judge (for construction-time filtering) and one of the evaluated agents (Table 2), yet scores mid-pack (2.42, below three Gemini variants and above only the smaller open models) — no visible score inflation for the judge's own family in the leaderboard. This is a soft, single-paper data point against strong self-preference contamination in this specific case, not a general result; it doesn't rule out subtler effects (e.g. inflated scores specifically on episodes the same model both filtered and later solved), which the paper does not check.

## Statistical treatment — explicit gap, same shape as ObjView-Bench's gap

No confidence intervals, no variance/std across episodes, no stated number of independent runs/seeds per model, no significance testing anywhere in the paper. All leaderboard numbers are single point-estimate averages over the 377-episode test split (or the full 2,014, unclear which split Table 2 aggregates over — not explicitly stated in the fetched sections). Like ObjView-Bench, they substitute *episode-count scale* (hundreds of episodes) for *trial replication*; not directly reusable for our few-objects/few-trials regime (Q12).

## What transfers to our setting

- **The "unanswerable from a single/default view" validation gate itself (core steal, per the framing doc's selection rationale)**: a concrete, implementable check — before trusting an inspection task as a genuine view-selection test, verify a judge (or, in our geometry-grounded setting, a metric) cannot resolve it from the current default/uniform-sphere view or from a non-orthogonal view. Directly actionable for constructing our own benchmark tasks (Q11 dataset design, and arguably Q7's metric-family question — "does the metric saturate at the wrong view" is the geometric analogue of "is the question answerable from the wrong view").
- **GT-view-for-scoring-only separation (Q3, Q10 framing)**: the goal image is fed only to the judge, never to the agent — a clean, working precedent for "GT used to score, not to solve," directly matching our framing doc's stated design ("the GT goal view used for scoring only"). This is a real, if partial, answer to Q3: their separation is *provenance of information flow* (GT reaches the scorer, not the policy), not *construct* (their judge and their GT still come from correlated sources — see below) — so it only partially satisfies the self-preference-literature bar the branch question sets.
- **VQA-at-goal ceiling check (Q7/Q14 analog)**: their static "give the model the human GT view directly" baseline (3.58, ≈ human 3.53) is a clean, reusable pattern for an oracle-view condition — feed the analytically/metric-optimal view directly to the downstream reasoner and see how close that gets to a ceiling, isolating "answering" quality from "finding" quality. Directly reusable structure for our Q14 (oracle-selector condition, action-space-quality vs. policy-quality separation), even though their oracle is a human label and ours would be an analytical/metric-based view.
- **The view-correct/answer-correct conflation as a documented, self-reported failure mode (Q15)**: the paper's own limitations section names the exact problem Q15 asks about, without solving it — strong secondary justification for building the view-correct × answer-correct grid ourselves, since even a well-resourced benchmark with 1,120 human-annotation hours ran into this and left it unresolved.
- **Judge weak-correlation caution (Q17)**: ρ=0.54 Spearman against human judgment, self-described as merely "reasonable," is a useful calibration point for how much to trust a single un-anonymized, non-position-swapped, single-model VLM judge — if this is the bar a heavily-resourced benchmark clears, our own judge protocol (if any) needs the controls (multiple judges, anonymization, position swap, held-out human slice) this paper lacks, per Q17's own list.
- **Discrete, small, fixed-granularity action space as a tractability pattern (Q6/RQ4 in framing doc)**: 0.25 m / 30° discrete steps with a hard 25-step cap and a model-emitted `stop` action is a concrete, working example of keeping a continuous-feeling space navigable for a VLM by discretizing finely rather than pre-enumerating labeled views — a different design point on the same axis our RQ4 is exploring, worth comparing against our label-a-set-of-views approach.
- **Static-baseline decomposition (Table 3) as a methodology template**: blind / fixed-start / fixed-overview / goal-view baselines is a clean four-point calibration ladder that isolates "does the model need vision at all" → "does it need to move" → "would a generically good vantage help" → "does it succeed once vision is sufficient." Reusable scaffold for our own baseline suite (Q5).

## What does NOT transfer, and why

- **No geometric ground truth anywhere (Q2, Q4, Q10)**: there is no mesh, no point cloud, no depth channel, no primitive fit, no surface normal, no coverage/Chamfer metric — the entire GT and scoring pipeline is human-labeled-viewpoint + VLM-judge-on-RGB. Zero evidence for Q2 (does an analytical face-normal-through-centroid GT survive a defective survey cloud — the paper has no survey cloud, no cloud-fitting step at all) and zero evidence for Q4 (mesh-vs-real-defect GT strategies aren't discussed; their "GT" is a human pointing at a good vantage, not a geometric fact derived from any 3D model).
- **No sensor-defect injection, no pose error, no dropout, no fusion offset (Q9, Q10)**: 3DGS scenes are rendered directly with no depth sensor simulated at all — there is no "single-view depth vs. fused-cloud depth" concept in this pipeline because there's no depth-based fusion anywhere. Q9 and Q10 get zero evidence from this paper; it's an RGB-only benchmark by design, explicitly chosen because 3DGS "preserves fine-grained visual details... often degraded in mesh-based simulators" (the paper's whole rationale for the representation choice is orthogonal to our geometric-fidelity concern).
- **No orthogonality-to-surface concept at all (Q7)**: "good view" here means "view that visually disambiguates an attribute/count/relation," never "view whose optical axis is normal to a surface." There is no per-primitive analytical optimum, no ceiling-score concept tied to geometry — the entire evaluative vocabulary is semantic/informational, not geometric. Zero transfer to Q7's metric-family question.
- **No symmetry/view-equivalence machinery beyond an unspecified viewpoint set (Q8)**: 𝒱_ans is stated to be a set of valid viewpoints (plural), and Appendix 0.E mentions handling "valid but unannotated alternatives via reference comparison" — but there is no explicit equivalence relation, no reported set cardinality, and no discussion of *why* a viewpoint is equivalent (symmetry of the object vs. simply "also happens to show the label"). This is a much looser, ad hoc version of what Q8 needs (a defined equivalence relation respected by an addressing scheme) — useful only as a pointer that "multiple GT views, judged by reference-comparison at score time" is one loose pattern, not as an answer.
- **Unit of evaluation is whole-episode, not per-region (Q1)**: episodes are scored holistically end-to-end; there is no notion of "surface region" at all since objects are rendered scenes, not primitives with faces. This maps onto our Q1's *second* option (object, question episode scored end-to-end) as a working real-world instance — useful as evidence for what that option looks like in practice and what it costs (exactly the view/answer-conflation problem above), which is itself an argument for our branch to prefer the (object, region) unit instead, if we want to avoid inheriting this specific failure mode.
- **VLM judge is not held separate from VLM construction, and neither is triangulated against a third-party/held-out metric implementation (Q3)**: both the "is this question hard enough" filter and the "is this answer correct" scorer are judge-model calls from closely related models (GPT-5.1 family), with no reimplementation-as-held-out-score and no third construct entirely outside VLM judgment (e.g. a geometric or physical ground truth) backing either stage. Per the branch's own self-preference framing, this is closer to "shared assumptions" than to a genuine separation — E3VS-Bench does not clear the bar Q3 sets, it only partially clears it via the GT-for-scoring-only information-flow separation noted above.
- **No statistical treatment (Q12)**: as with ObjView-Bench, point estimates over hundreds of episodes substitute for trial replication; not a transferable recipe for a few-objects/few-trials regime.
- **No real-robot / real-camera component at all**: fully simulated 3DGS scenes, no discussion of IK, reachability, or hardware; not relevant to our platform constraints beyond the general action-space-discretization pattern already noted.

## Relevance summary

Highest-value contribution is **methodological, not metric-transferable**: the two-gate "unanswerable blind AND unanswerable from initial/default view" filter is a directly reusable validation check for constructing genuine view-selection benchmark tasks (the paper's own stated reason for selection), and the GT-view-fed-to-scorer-only pattern is a working, if only partial, precedent for Q3's separation concern. It also self-documents, in its own limitations section, exactly the view-correct/answer-correct conflation Q15 warns about — useful as an existence proof that this failure is real and unresolved even under heavy annotation investment (1,120 hours). Everything downstream of "what is a good view" is semantic/VQA-shaped in this paper, not geometric — it supplies **zero** evidence for Q2, Q4, Q7, Q9, Q10, and only loose/partial evidence for Q3 and Q8. Treat it as a benchmark-construction-methodology reference for the VLM-orchestrator layer of our system, not as a source of geometric GT strategy, sensor-defect protocol, or orthogonality metric.
