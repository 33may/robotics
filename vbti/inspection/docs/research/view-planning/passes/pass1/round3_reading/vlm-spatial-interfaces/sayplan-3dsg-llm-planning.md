## Core method / idea

SayPlan grounds LLM task planning in a pre-built **3D scene graph (3DSG)** — a hierarchical multigraph with 4 levels (floor → room → asset/object, plus pose nodes for topology, Fig. 2) — by giving the LLM two API surfaces instead of one flat context dump:

1. **Semantic Search stage** (Algorithm 1, lines 1–7, p.4): the full graph 𝒢 is first `collapse()`-d to expose only the top level (floor/room names). The LLM is then given this collapsed graph plus the instruction and must issue `expand(node_name)` / `contract(node_name)` API calls in a loop until it declares the subgraph 𝒢′ sufficient. A running `Memory` list of previously-expanded nodes is passed back in each turn so the LLM doesn't re-expand nodes it already rejected (Markovian search without full interaction history).
2. **Causal Planning / Iterative Replanning stage** (Algorithm 1, lines 8–13): given 𝒢′, the LLM emits a high-level plan of `goto`/`pickup`/`access`/`open`/`release`/etc. actions over *nodes* only — a classical path planner (Dijkstra) is delegated the job of connecting `goto(room)` to `goto(room)` via intermediate pose nodes, shortening the LLM's planning horizon. The full plan is then forward-simulated by a **scene graph simulator** `verify_plan()`, which returns textual feedback on the first violated precondition (e.g. *"cannot pick up banana"*, *"coffee mug is not accessible"*) — the LLM revises and resubmits until `verify_plan` returns success or a 5-iteration cap is hit.

The scene graph itself is JSON-text-serialized (NetworkX graph → JSON), e.g. a single asset node: `{name: coffee_machine, type: asset, location: kitchen, affordances: [turn_on, turn_off, release], state: off, attributes: [red, automatic], position: [2.34, 0.45, 2.23]}`, edges as `{kitchen↔coffee_machine}` (§3.2, p.4). Note: metric `position` is carried as a node attribute for the *path planner and simulator* to use — the LLM itself only ever emits actions on named nodes (`goto(pose13)`, `access(cabinet5)`), never coordinates. The static system prompt (agent role, function signatures, state predicates, output-JSON schema, one worked example) is ≈3900 tokens and is identical across both stages and across all task instructions/environments (Appendix J, p.48, reproduced verbatim in that appendix).

## Concrete results / numbers

Evaluated on two environments: **Office** (37 rooms, 151 assets/objects, single floor, real environment with real-robot execution) and **Home** (Stanford 3DSG "Klickitat" — 28 rooms, 112 assets/objects, 3 floors). 90 task instructions across 4 families: Simple Search (30), Complex Search (30), Simple Planning (15), Long-Horizon Planning (15) (Table 6, full instruction lists in Appendix C).

- **Semantic search success (Table 1, p.6):** Human baseline 100% on everything (both envs, both difficulty levels). **SayPlan(GPT-3.5) fails almost completely**: 6.6% simple / 0.0% complex (Office), 0.0% / 0.0% (Home) — the paper states GPT-3.5 "consistently failed to reason over the input graph representation, hallucinating nodes to explore or stagnating at exploring the same node multiple times." **SayPlan(GPT-4): 86.7% simple / 73.3% complex, identical on both Office and Home.** This is the paper's own load-bearing capability floor: even the best model loses ~13pp going simple→complex and never reaches human parity.
- **3DSG token footprint (Table 2 / Tables 4–5, p.7/p.13-14):** Office full graph 6731 tokens (407 entities: 37 rooms, 73 assets, 78 objects, 1 agent, 218 edges) → collapsed 878 tokens (105 entities). Home: 6598 → 1817 tokens. **Table 2's own "Compression Ratio" column reports 86.9% (Office) and 72.5% (Home)**, computed as `1 − collapsed/full`; **the body text on the same page instead states "82.1%... and a 60.4% reduction"** — these two numbers do not match each other and neither matches my own recomputation from Tables 4/5 (which gives 86.9%/72.5%, agreeing with the table, not the prose). Flagging this as an internal inconsistency in the paper itself, not resolvable from the text given — cite the table numbers (86.9%/72.5%), not the abstract's "82.1%" figure, if a precise number is needed.
- **Causal planning correctness/executability (Table 3, p.6):** SayPlan vs. two ablation baselines (LLM-As-Planner: full plan in one open-loop shot; LLM+P: path-planner delegation only, no iterative replanning):

  | Method | Simple Corr | Simple Exec | Long-Horizon Corr | Long-Horizon Exec |
  |---|---|---|---|---|
  | LLM+P | 93.3% | 13.3% | 33.3% | 0.0% |
  | LLM-As-Planner | 93.3% | 80.0% | 66.7% | 13.3% |
  | SayPlan | 93.3% | 100.0% | 73.3% | 86.6% |

  Correctness (does the plan match human intent) is essentially flat across methods and driven by the base LLM, not the scaffolding — **executability is where the iterative-replanning + simulator-feedback loop earns its keep** (13.3%→86.6% on long-horizon). Error-type breakdown (Table 3 right): SayPlan's only remaining error category after replanning is **hallucinated nodes, 6.67%** — missing/wrong-action and missing-pose errors go to exactly 0% for SayPlan, vs. LLM-As-Planner's 60% missing-pose rate. 2 of 15 long-horizon tasks never reached an executable plan even after the 5-iteration replanning cap ("I'm hungry, bring me an apple..." and the rotten-apple-cabinet task — Table 18, p.32).
- **Named, reproducible failure modes** (§5.1, p.7, and cross-checked against the full search-sequence tables in Appendix F): (a) **negation failure** — "consistently failed when presented with questions such as *'Find me an office that does not have a cabinet'* or *'Find a bathroom with no toilet'*" (one of two negation-search instructions in Appendix F Table 13 shows SayPlan giving a wrong answer, `nikos_office`, vs. human's correct `tobis_office`); (b) **distance/count-based reasoning failure** — "the LLM's failure to conduct simple distance-based and count-based reasoning over graph nodes... While trivial to a human, this does require the LLM agent to reason over multiple nodes simultaneously, where it tends to hallucinate or miscount connected nodes" — confirmed in Appendix F: "closest fire extinguisher to the manipulation lab" and "closest meeting room to the kitchen" both fail (Table 14, p.26); (c) breadth-first exploration when no semantic cue is present in the instruction (e.g. "find object K31X"), i.e. the model falls back to exhaustive search rather than targeted reasoning when node names carry no information.
- **Scalability ablation (Appendix H, Figs. 7–8, p.46):** environment size swept 30→300 room nodes (collapsed-graph scale). **All failures at scale were caused by exceeding GPT-4's 8192-token context limit, not by degraded reasoning from added distractor nodes** — quoted directly: "all the failures that occurred across both semantic search and iterative replanning were a result of the LLM's input exceeding the maximum token limits... this indicates that the LLM's reasoning capabilities or ability to attend to the relevant parts of the 3DSG is not significantly impacted by the presence of 'noisy' or increasing number of nodes." The cost of scale is more search steps to converge, not more errors per step.
- **Real-world deployment:** plans executed on a Franka Panda arm + Omron LD-60 mobile base with LiDAR localization against the pre-built Office 3DSG (Appendix I, Fig. 9, p.47) — pick/place/open/close skills via a separate RGB-D grasp-detection + behaviour-tree module [Haviland et al.], not derived from the 3DSG or the LLM.

## Load-bearing assumptions

- **The 3DSG is pre-built and assumed static post-map-generation.** §6 (Limitations, p.8) states this explicitly: "SayPlan's current framework is constrained by the need for a pre-built 3D scene graph and assumes that objects remain static post-map generation, significantly restricting its adaptability to dynamic real-world environments." SayPlan never perceives anything at planning time — there is no vision subagent, no camera, no render, anywhere in the loop. All "grounding" is symbolic-graph grounding, not visual grounding.
- **Nodes carry closed-vocabulary, purely textual descriptions.** Future-work note (§6): "the incorporation of open-vocabulary representations within the scene graph could yield a general scene representation as opposed to solely textual node descriptions" — i.e. even the authors flag that the current system's entire spatial world is names, attributes, and predicates, nothing perceptual.
- **The scene graph simulator's predicate set is hand-authored and assumed complete.** §6: "a potential limitation of the current system lies in the scene graph simulator and its ability to capture the various planning failures within the environment. While this works well... for more complex tasks involving a diverse set of predicates and affordances, the incorporation of relevant feedback messages for each instance may become infeasible."
- **Infeasibility is handled reactively, not proactively.** There is no upfront filtering, no affordance score, no "unavailable" marker shown to the LLM before it commits to an action (contrast SayCan-style affordance weighting). The LLM can propose any action on any node it has expanded; only after a full forward-simulate pass does `verify_plan()` return a single textual message identifying the *first* violated precondition. The LLM then revises the whole plan and resubmits — capped at 5 iterations, with real (2/15) long-horizon task failures when that cap is hit.
- **Search termination is self-declared by the LLM** (`mode: "exploring"` → `mode: "planning"` in the output JSON, Appendix J), with no external stopping-criterion check — it is exactly the LLM's own judgment of "have I seen enough" that produces the incomplete-search errors in Table 3 (3.33% for LLM+P; near-zero elsewhere because SayPlan's replanning loop catches most of what falls through).
- **Node addressing is by human-readable name, never by coordinate or arbitrary index** (`kitchen`, `postdoc_bay2`, `pose13`, `cabinet5`) — this is demonstrated, not ablated: the paper never tests numeric/index addressing as an alternative and states informally (in the qualitative discussion, p.7) that "meaningful node names and attributes" are what let the LLM "relate the query instruction for efficient search" — i.e. semantic legibility of the identifier is treated as necessary, but this claim has no controlled comparison against opaque IDs.

## What transfers to our setting

- **The collapse/expand pattern is the canonical worked example of RQ4's "on-demand exposure" option**, and it is exactly what the branch-selection rationale flagged it for. Its concrete payoff (86.9%/72.5% token reduction, near-constant token footprint via `contract`, Fig. 3) is real and measured — but it is a *scale* solution: it exists to keep hundreds-of-nodes environments under an 8192-token budget. Directly answers the branch question "is there evidence that dumping a small space is worse than exposing it through a query": **no such evidence exists in this paper** — the scalability ablation's smallest tested point is already 30 room nodes (≈100+ total entities before collapse), an order of magnitude above a face/view action space for one tabletop primitive (tens of views at most). At our scale, SayPlan gives no reason to adopt collapse/expand's added search-protocol complexity (which itself is where GPT-3.5 fails outright and where hallucinated/miscounted-node errors persist even for GPT-4).
- **Direct, reusable design element for the discrete-action-menu question (RQ3/RQ4):** named, semantically legible node IDs over coordinate/index IDs, with metric pose carried as a side-channel attribute for the executor (path planner / IK) rather than something the LLM reasons over directly. This is one concrete, deployed data point for the branch's pose-encoding question ("names vs. integers/indices vs. coordinates") — SayPlan's answer is names-only for the LLM-facing interface, coordinates strictly for the non-LLM executor. Not an ablation (no comparison condition run), so it's a demonstrated pattern, not resolved evidence — flag accordingly in the evidence-discipline table.
- **The iterative-replanning-with-simulator-feedback loop is a concrete, measured (13.3%→86.6% executability, Table 3) precedent for "ask better questions instead of showing more"** (relevant to the RePLan-adjacent branch question on caption-hand-off recovery): a purely textual feedback signal identifying *the first violated precondition* is enough to drive dramatic executability gains without any visual information at all — evidence that some fraction of the "blind orchestrator" problem is recoverable through structured symbolic feedback, not necessarily vision. Useful as a floor/baseline: if a textual constraint-violation message (e.g. "no view exists orthogonal enough to face 3" or "candidate view fails IK") gets us most of the way there, that bounds how much visual feedback we actually need to add on top.
- **A concrete instance of Q12 (how should infeasible options appear):** SayPlan's answer is "reactive rejection with a single textual diagnostic," not "silently removed," "marked unavailable up front," or "affordance-scored" (SayCan-style). This is a fourth pattern worth adding explicitly to that branch question's option set, with a measured cost: it needs multiple replanning rounds (mean not reported, but individual tasks needed up to 5) and 2/15 long-horizon tasks in this paper never converged within the iteration cap — i.e., reactive-only rejection has a real, non-zero failure rate even with unlimited symbolic (non-visual) precision.
- **The scalability ablation's clean separation of "reasoning degrades" vs. "context window exceeded"** (Appendix H) is a useful methodological pattern for our own benchmark design: when we test count/size effects on our (much smaller) action space, we should distinguish "model gets confused by more options" from "model runs out of context," since SayPlan found the latter, not the former, was the actual failure mechanism at their scale.
- **Confirms named, reproducible LLM spatial-reasoning failure modes to hand to Branch 2 as test cases**, per the branch's explicit ask: negation queries ("a face that is *not* orthogonal to X"), count/distance-based comparison ("the closest face to Y"), and hallucinated/miscounted graph nodes under multi-node aggregation — all observed here in a pure-text, no-image setting, meaning these failures are not an artifact of visual grounding and would need to be tested even for a blind text-only action menu.

## What does NOT transfer, and why

- **No visual grounding anywhere — the paper cannot speak to any of the "seeing" branch questions (marked renders, sparse/defective point clouds, view-selection chicken-and-egg problem, image-vs-text encoding).** SayPlan's "3D scene graph" is a fully pre-processed symbolic map (rooms, assets, predicates) built offline by other SLAM/3DSG systems (Kimera, Hydra, cited but not run here) — there is no render, no camera, no point cloud shown to the LLM at inference time, ever. Do not cite this paper for anything about defective clouds, colourless geometry, or view-render fidelity (branch questions on GraspView/SPAZER/VLM3D/SeqVLM territory); it is silent on all of it by construction.
- **No spatial-relation/adjacency reasoning is tested at all** — SayPlan's graph encodes room↔asset↔object containment and floor↔room topology (pose-node paths for navigation), never geometric relations like "orthogonal to," "opposite face," "rotated 90° from." The closest analogue (distance-based reasoning: "closest fire extinguisher to the manipulation lab") is a *named failure mode*, not a success — reinforcing rather than contradicting the branch's capability-floor concern (MMSI-Bench/ViewSpatial/SpinBench), but from an entirely different task family (topological room-graph distance, not camera-relative viewpoint geometry) — don't over-extend this as direct evidence for the ego/allo or face-adjacency questions; it's suggestive corroboration at best, not a measurement of the same construct.
- **The "hierarchy" being collapsed/expanded is a containment hierarchy (floor⊃room⊃asset⊃object), not a viewpoint/pose hierarchy.** There is no notion in this paper of a small closed set of *camera poses* relative to one object needing hierarchical exposure — the entire mechanism is designed for and validated on *environment-scale* multi-room graphs. Reusing "collapse/expand" for a face/view hierarchy is a structural borrow, not a validated transfer — the paper offers zero evidence about whether collapse/expand helps or hurts at the scale of "6 box faces" or "12 cylinder orbit positions," where a flat dump is almost certainly cheaper and simpler (per the token-budget-only failure mode found in Appendix H, there's no reason to think 10-50 entities would ever approach the token ceiling that motivates collapsing in the first place).
- **No ablation of the graph *encoding* itself (JSON vs. alternative text formats, hierarchical levels chosen vs. flat, node-name-semantic vs. opaque-ID) — everything ablated is *algorithmic scaffolding* (iterative replanning, path-planner delegation, model capability GPT-3.5 vs GPT-4, environment scale), not representation choice.** For the branch's evidence-discipline question, SayPlan's central "hierarchical JSON scene graph" claim is **demonstrated at scale, not comparison-ablated against alternative encodings** — no controlled comparison exists here for "does this encoding beat a flatter/simpler one," only for "does the search+replanning scaffolding beat naive single-shot planning" (Table 3) and "does node-count scale break the LLM" (Appendix H, Figs. 7-8). Cite Table 3 and Figs. 7-8 as ablations; do not cite the JSON-graph representation itself as an ablated finding.
- **The one clear inter-model comparison here (GPT-3.5 vs GPT-4, Table 1) is a capability-floor data point, not an encoding comparison** — it says "small/older models cannot do this kind of graph-structured spatial reasoning at all (6.6%/0% vs 86.7%/73.3%)," reinforcing the branch's general concern about capability floors, but it says nothing about which *encoding* of a fixed capability model performs best, so it cannot resolve the branch's pose-encoding contradiction (Thinking-with-Novel-Views vs. MapGPT) — flag as capability evidence, not encoding evidence, in any evidence table built from this branch.
- **Real-world validation is a single generated long-horizon plan replayed on a real robot for illustration (Fig. 9), not a controlled real-world success-rate study** — all quantitative results (Tables 1–3, Figs. 7–8) are evaluated against the pre-built simulator/graph, not against physical execution outcomes. Do not cite this paper for any claim about real-world (as opposed to plan-level) success rates.

**Note on relationship to the branch's framing:** SayPlan is the strongest available real-system precedent for RQ4's "on-demand exposure vs. full dump" question, but its evidence base is calibrated to environment-scale graphs (hundreds of nodes), not object-scale action spaces (tens of views). Its main transferable lessons for our actual scale are (a) named > coordinate addressing for the LLM-facing interface, (b) reactive symbolic feedback (verify-then-correct) measurably improves executability without any visual input, and (c) even the best current model (GPT-4) has a real, non-trivial ceiling on graph-structured spatial reasoning — negation, counting, and distance comparisons are named failure modes worth encoding as test cases regardless of whether our interface ends up blind or seeing.
