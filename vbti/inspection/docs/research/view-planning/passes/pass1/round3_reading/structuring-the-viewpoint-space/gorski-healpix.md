# Górski, Hivon, Banday, Wandelt, Hansen, Reinecke, Bartelman — "HEALPix: A Framework for High-Resolution Discretization and Fast Analysis of Data Distributed on the Sphere"

ApJ 622:759–771 (2005); arXiv:astro-ph/0409513v1. Full text obtained (21-page PDF via arXiv, converted with `pdftotext -layout`, all equations/figure captions present) and read in full.

This is an astrophysics/numerical-methods paper about discretizing the celestial sphere for CMB (cosmic microwave background) map analysis. There is **no object, no vision, no robot, no camera pose** anywhere in it — it tessellates an abstract unit sphere of *directions*, full stop. Everything below is read through that lens: HEALPix is the clean, well-engineered exemplar of category **(a) index into a global tessellation** from Branch Question 1, and the task is to extract exactly what that buys and what it cannot buy.

## Core method

**Section 3 (p.5), the three requirements.** The paper states three desiderata for a sphere pixelization used for large-scale data analysis, and asserts (with a table of five competing schemes, p.5–6) that no prior scheme satisfies all three simultaneously:
1. **Hierarchical structure** — "data elements which are nearby in a multi-dimensional configuration space... are also nearby in the tree structure of the data base," enabling fast nearest-neighbour lookup and wavelet transforms.
2. **Equal area** of all cells — so uniform instrument noise integrates to uniform pixel-space noise, with no regional density bias.
3. **Iso-latitude** distribution of cell centers — essential for fast spherical-harmonic evaluation (see Results below).

Competing schemes each satisfy at most two: QuadCube (COBE's pixelization) gets 1+2 but not 3; Equidistant Cylindrical Projection gets 1+3 but not 2 (oversamples near poles); icosahedral/hexagonal grids get 2 but not 1 or 3; "igloo" grids get 3 but trade off 1 or 2; GLESP gets accurate quadrature but isn't hierarchical at all (Sec 3, p.5–6).

**Section 4 (p.6), general construction.** The generic recipe: partition the sphere into curvilinear quadrilaterals (base-level tessellation); if each base cell maps onto `[0,1]×[0,1]`, a nested `n×n` subdivision of the square gives a quad-tree "trivially." For `n=2` (i.e., quadrupling each cell per refinement level) this "admits an elegant binary indexation" (Fig. 1) — the same indexing trick already used in QuadCube. The base-level tessellation itself is parametrized by `Nθ` (number of pixel rings pole-to-pole) and `Nφ` (meridional-cut multiplicity); `Npix = Nθ·Nφ`, `Ωpix = 4π/(Nθ·Nφ)`, and equal-area-ness of the polar caps vs. equatorial belt requires a specific colatitude `θ⋆` where they meet: `cos θ⋆ = (Nθ−1)/Nθ` (Eq. 1, p.6–7). The authors chose `Nθ=3, Nφ=4` — 12 base pixels — and call that choice "HEALPix" (Sec 4, p.7).

**Section 5 (p.7), the HEALPix grid.** Base resolution = 12 pixels in 3 rings (one polar cap ring north, one equatorial ring, one polar cap ring south — actually described as "twelve pixels in three rings around the poles and equator"). Resolution parameter `Nside` = number of subdivisions along a base-pixel edge needed to reach the target resolution. **`Npix = 12·Nside²`**, all pixels of identical area **`Ωpix = π/(3·Nside²)`** (Sec 5, p.7, unnumbered display equations). Equatorial-zone rings each hold `Neq = 4·Nside` pixels; polar-cap rings hold a varying count that grows by 1 pixel per ring per quadrant moving away from the pole.

**Section 5.1 (p.7–9), pixel positions — closed form, no lookup table.** Given `Nside` and a ring/column index, pixel-center `(z=cosθ, φ)` is obtained by direct formulas (Eqs. 2–9): ring index `i`, in-ring index `j`, then `z = 1 − i²/(3Nside²)` (north polar cap, Eq. 4) or `z = 4/3 − 2i/(3Nside)` (north equatorial belt, Eq. 8), and `φ` from `i,j` and a parity-dependent phase shift `s` (Eqs. 5, 9). Southern hemisphere is the mirror image. **This is a fully analytic map from index to direction — no precomputed table needed for the basic pixel↔coordinate transform.**

**Section 5.2 (p.9–10), the two numbering schemes — this is the load-bearing section for our branch.**
- **RING scheme**: count pixels moving down from north to south pole along each iso-latitude ring. Stated purpose: "It is in this scheme that Fourier transforms with spherical harmonics are easy to implement." This is a flat sequential index optimized for a numerical-analysis workload, not for spatial locality or hierarchy.
- **NESTED scheme**: replicates the QuadCube tree structure. Base-resolution pixel `f ∈ [0,11]` is the address *prefix*. Within a base pixel, the nested index `p′n = pn mod Nside²` has binary representation `[...b2 b1 b0]₂`; even-position bits give local coordinate `x = [...b2 b0]₂` (Eq. 13), odd-position bits give `y = [...b3 b1]₂` (Eq. 14); `v=x+y, h=x−y` (Eqs. 15–16) recover the ring index `i` (Eq. 17) and longitude index `j` (Eq. 18) — i.e. address → direction is again closed-form, this time via bit-deinterleaving instead of the RING arithmetic.
  - **Fig. 1 and its caption are the exact mechanism the selection rationale flagged**: starting from a coarse `2×2` grid (indices `00₂,01₂,10₂,11₂`), each "Prograde" (refine) step subdivides every pixel into 4 daughters that "inherit the pixel index of their parent (boxed) and acquire two new bits to give the new pixel index" (Fig. 1 caption, p.15). Concretely: parent `11₂` (=3) has children `1111₂=15, 1110₂=14, 1101₂=13, 1100₂=12`; parent `01₂` (=1) has children `0111₂=7, 0110₂=6, 0101₂=5, 0100₂=4`; and so on. "Degrade" (coarsen) is the inverse — drop the last 2 bits, i.e. `pn >> 2`.
  - The paper is explicit that a full nested address is a **prefix + path**: "Several such curvilinearly mapped coordinate patches (12 in the case of HEALPix...) are joined at the boundaries to cover the sphere. All pixel indices carry a prefix (here omitted for clarity) **which identifies which base-resolution pixel they belong to**" (Fig. 1 caption, p.15). So the full address at resolution `Nside=2^k` is: base-pixel `f∈{0..11}` (4 bits), then `k` quaternary digits, each digit literally naming "which of the 4 children" at that refinement level — a genuine path-like address, not a black-box integer.
  - **What NESTED buys, per the paper**: "efficient... nearest-neighbour searches (see Wandelt, Hivon, and Górski 1998)" and "an immediate construction of the fast Haar wavelet transform." Note the neighbor-search algorithm itself is *cited*, not derived in this paper — HEALPix's own text does not give the neighbor-finding procedure, only asserts it exists and is efficient. This matters for Branch Q4/Q7: the bit-based address gives O(1) parent/child navigation for free, but cross-base-pixel (cross-"seam") adjacency needs a separate, non-trivial algorithm referenced but not shown here.

**Section 5.3 (p.10–11), pixel boundaries.** Boundaries are non-geodesic and analytically simple: `cosθ = a + b·φ` in the equatorial zone, `cosθ = a + b/φ²` in the polar caps (Eqs. 19–22) — chosen specifically so cell areas can be checked/derived by direct integration, not numerically.

**Table 1 (p.14)**: `Nside=2^k` for `k=0..17` (and asymptotically to `k=29`), giving `Npix=12·Nside²` and angular resolution `θpix=√Ωpix`. E.g. `Nside=1→Npix=12, θpix=58.6°`; `Nside=1024→Npix≈12.6M, θpix≈3.44′`; `Nside=8192` (the practical ceiling under 32-bit signed integer indexing) `→Npix≈805M, θpix≈25.8″`; 64-bit integers extend this to `Nside=2^29`.

## Concrete results and numbers

- `Npix = 12·Nside²`, `Ωpix = π/(3·Nside²)` — exact, closed-form, chosen a priori by picking one integer parameter (Sec 5, p.7).
- Table 1 (p.14): full enumeration from `Nside=1` (12 pixels) to `Nside=2^29` (≈3.46×10¹⁸ pixels, θpix≈3.93×10⁻⁴″); 32-bit signed-int indexing caps practical use at `Nside≤8192` (≈805M pixels).
- **Performance**: iso-latitude structure gives spherical-harmonic transform cost scaling as `~Npix^1.5`, versus `~Npix²` for non-iso-latitude grids, "entirely geometrical" — because associated Legendre functions need evaluating only once per ring rather than per pixel (Sec 6, p.11, Figs. 6–7 give the visual comparison against QuadCube, icosahedral, and ECP grids). Global spherical-harmonic analysis+synthesis of a multi-million-pixel map costs "about 10³s of a standard serial machine CPU time" (Sec 6, p.11–12).
- **No timing numbers are given for the pixelization/addressing operation itself** — only for the downstream harmonic-transform workload. Address↔direction lookup is analytic (Eqs. 2–18), i.e. effectively O(1) per query with no reported benchmark because it doesn't need one.
- Adoption list (Sec 7, p.12–13): Boomerang, Archeops, TopHat, WMAP, Planck (all CMB missions), plus the Sloan Digital Sky Survey.

## Load-bearing assumptions

- **The domain is a topologically fixed, single, always-identical sphere.** There is exactly one "shape" ever pixelized — the paper never has to solve the problem of the same address meaning different things (or needing different structure) on different objects, because the object never varies. This is the single biggest disanalogy with our setting.
- **The quantity being discretized is a direction (a point on `S²`), not a camera pose.** No orientation/roll, no radius/distance, no "looking at a target" semantics. `(z=cosθ, φ)` fully specifies a HEALPix cell; there is no analog of an up-vector or a stand-off distance anywhere in the formalism.
- **The 12-base-pixel/octahedral symmetry is fixed by the `Nθ=3, Nφ=4` design choice** (Sec 4, p.6–7) — a choice justified entirely by wanting to simultaneously satisfy the three requirements for *this* application (fast harmonic transforms on CMB data), not by any property of an inspected object.
- **Requirement 3 (iso-latitude) is motivated purely by a numerical-analysis workload (Legendre-polynomial recursions) that has no counterpart in our task** — we never evaluate spherical harmonics on our view space.
- The "efficient nearest-neighbour search" claim for NESTED addressing is a citation to a separate 1998 paper (Wandelt, Hivon, Górski), not something this paper derives or benchmarks itself.

## What transfers to our setting

- **Confirms and sharpens the taxonomy in Branch Q1.** HEALPix is a textbook-clean instance of category (a) — "index into a global tessellation" — and it demonstrates that within that category there can be *two different addressing conventions for the same cells* optimized for different consumers: RING (flat sequential, optimized for a downstream numerical algorithm) vs. NESTED (hierarchical prefix+path, optimized for locality/neighbor-finding/multi-resolution). That split — "sequential index for the math, hierarchical path for the topology" — is a useful design vocabulary even if our address space is nothing like a sphere.
- **The NESTED "parent-ID + 2 bits" mechanism is a genuine, verified precedent for a path-like, LLM-legible address** (Fig. 1 caption, p.15: children "inherit the pixel index of their parent... and acquire two new bits"). If any future geometry-conditioned scheme wants a hierarchical address (e.g. coarse region → sub-patch → sub-sub-patch on a face), this is a concrete, closed-form pattern to imitate: prefix names the coarse cell, each subsequent digit names "which quadrant," and both directions (refine/coarsen) are one bit-shift each.
- **The address explicitly encodes provenance of the "seam" rather than hiding it** — directly answers Branch Q7 in the general case: "All pixel indices carry a prefix... which identifies which base-resolution pixel they belong to" (Fig. 1 caption). HEALPix does not pretend the 12-base-pixel boundary doesn't exist; it bakes it into the address as the leading field. Evidence that a seam-aware scheme can still be a single flat namespace, as long as the seam ID is a first-class prefix rather than something the consumer has to infer.
- **Bounded-cardinality-by-construction is real and cheap when the domain is fixed**: `Npix=12·Nside²` lets you promise an exact, pre-known view count by picking one integer (relevant to Branch Q13). This is genuine positive precedent for "a discrete address space with a closed-form size formula" as a *design pattern* — but see below for why the guarantee itself doesn't transfer.
- **Requirements-as-checklist methodology (Sec 3) is reusable independent of the specific three requirements.** The paper's approach — state the desiderata *first* (hierarchy, uniformity, workload-alignment), then show no prior scheme satisfies all of them simultaneously, then construct one that does — is a clean template for how the synthesis could argue for a novel geometry-conditioned scheme: name the requirements our task actually needs (e.g., "orthogonality-native," "primitive-anchored," "bounded per-primitive cardinality"), then show existing schemes (uniform sphere grids, aspect graphs, C-space) each satisfy some but not all.
- **Analytic (not tabulated) address↔pose resolution is a positive precedent for the PAMDP split (Branch Q3).** HEALPix resolves "which cell" → "cell center coordinates" via direct closed-form equations, not a lookup table or search — i.e., a genuinely deterministic `g(k) → x_k` map, the cleanest possible version of what the branch's PAMDP question asks for. It shows the "discrete symbol, deterministic continuous resolution" split is not just theoretically clean but has been engineering practice at scale (billions of pixels) for two decades.

## What does NOT transfer, and why

- **It does not deliver "the orthogonal view of face 3" as a native address (Branch Q2), and is in fact the poster child for the failure mode that question warns about.** A HEALPix cell names a *direction on an abstract sphere*; it has zero knowledge of any object, let alone a face normal. To use HEALPix for "look orthogonal to face 3" you would still compute face 3's normal direction and then do a nearest-neighbour lookup into the HEALPix grid to find which cell it falls in — exactly the operation the branch's framing document treats as the thing to avoid. This is precisely why the selection rationale calls it "the good version of our current uniform baseline": it is a better-engineered instance of the *same category* our current `{h,v}` scheme already belongs to, not a different, object-anchored category.
- **No pose/orientation is encoded at all** — no roll, no up-vector convention, no stand-off distance. Even granting that a cell names "which direction to look from," a full eye-in-hand camera pose needs more; HEALPix is silent on all of it.
- **Adjacency/neighbor-finding is not self-contained in this paper.** The NESTED scheme's within-base-pixel neighbor lookup is bit-arithmetic-cheap, but crossing a base-pixel boundary requires the algorithm of Wandelt, Hivon & Górski (1998), cited but not reproduced here — so "the paper" does not itself hand us a full closed-form adjacency definition, only an existence claim (relevant caveat for Branch Q5's adjacency-definition inventory: don't credit this document with more than it contains).
- **Zero treatment of variable arity or cross-shape consistency (Branch Q12/Q13/Q20).** There is exactly one topology ever pixelized (the sphere), so the question "does address `k` mean the same thing on a box as on a cylinder" cannot even be posed within this paper's scope — it offers no evidence either way, positive or negative, for RQ3's cross-shape view-addressing question. This paper is not a counter-example to the claimed literature gap; it simply never touches the cross-shape problem.
- **No feasibility/fallback concept whatsoever (Branch Q16).** Every direction on the sphere is always "valid" in this domain (there's no IK, no collision, no minimum shell radius for a telescope aimed at the CMB); nothing here informs how an address should behave when the corresponding view is infeasible.
- **The equal-area/iso-latitude requirements that drive the whole construction are workload-specific and do not apply to us.** We have no spherical-harmonic transform to accelerate and no white-noise-integration argument for wanting equal-area cells; importing HEALPix's specific `Nθ=3,Nφ=4` construction would be importing a solution tuned for a numerical-analysis problem we don't have.
- **The paper does not compare against any object/task-conditioned alternative** — it only compares against other *uniform*-sphere schemes (QuadCube, ECP, icosahedral, igloo, GLESP), all in category (a). This is a clean instance of the Branch Q19 finding: no source in this literature benchmarks a geometry-conditioned view space against a uniform sphere on a shared task/metric; HEALPix's own comparisons (Sec 3 table, Figs. 6–7) are uniform-vs-uniform, reinforcing that such a comparison is absent from the literature generally, not just missing from robotics papers.
- Not in this document (flagging so it isn't misattributed in synthesis): H3's 12-pentagon defect, `healpy` (the Python binding), S2 cells, and any comparison to Uber's H3 are **not discussed in this paper** — they are separate systems; if the synthesis wants that comparison it needs a different source.

## Liftable inventory (Branch Q18)

- Input requirement: none beyond "we're tessellating a sphere of directions." No mesh, cloud, or CAD features needed — it's not conditioned on any object.
- Implementation named in the paper itself: the HEALPix C/Fortran package, distributed since 1997 from `www.eso.org/science/healpix` (Sec 2, p.4). (The modern `healpy` Python binding is common knowledge but is *not* named in this 2005 paper — noting this so the synthesis doesn't cite the paper for something it doesn't say.)
- Build cost: effectively zero / closed-form for the pixelization and addressing themselves (Eqs. 2–18); the only reported cost (~10³s CPU for a multi-million-pixel map, Sec 6) is for the spherical-harmonic analysis workload we don't need.
