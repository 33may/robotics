Project site: https://sgmp-rss2024.github.io. **Domain note up front: this is a bimanual/parallel-jaw tabletop-manipulation RL paper — poking, grasping, placing objects — with zero content about cameras, viewpoints, visibility, or aspect graphs.** It was selected for this branch purely as a structural template for a "what/where/how" address, not for any viewpoint-specific finding; every claim below about "transfer" is a transfer of *addressing structure*, not of any manipulation result itself.

## Core method/idea

**Action = a triple (a^prim, a^loc, a^m) — "What, Where, How"** (§IV-A). Quote: "Our action representation comprises three key elements: the primitive type a^prim, the primitive location a^loc, and the primitive parameters a^m. These components collectively define the 'What', 'Where', and 'How' of each sequential skill execution."

- **a^prim ("what")**: discrete choice among **K=5 named motion primitives** (§IV-B, Appendix -A2): **Poke** (non-prehensile contact, a^m ∈ (−1,1)^5 = 2D gripper orientation + 3D post-contact motion), **Grasp** (a^m ∈ (−1,1)^2 = 2D orientation, then lift), **Move To** (a^m ∈ (−1,1)^5 = 2D orientation + 3D offset, relocates a grasped object to a chosen background point), **Move Delta** (a^m ∈ (−1,1)^5 = 3D translation + 2D rotation, only valid while grasping), **Open Gripper** (no parameters). Note: "primitive" here means *motion-skill type* (poke/grasp/…), a different sense from our framing doc's "object primitive" (box face / cylinder) — the two vocabularies are not interchangeable and the branch synthesis should keep them distinct even though the *tuple structure* maps cleanly (see "What transfers," first bullet).
- **a^loc ("where")**: "a selected point of interaction in the scene, **chosen from the observed point cloud** 𝒳" (§IV-A) — this is a **discrete index into the currently-observed point set**, not a regressed/continuous 3D coordinate and not a symbolic part label. The point cloud is pre-segmented into object 𝒳^obj and background 𝒳^b (assumption stated in §IV: "We further assume that this point cloud is segmented into object and background components"); Move-To's location is drawn from 𝒳^b specifically ("a^loc ∈ X^b"), the other primitives from 𝒳^obj.
- **a^m ("how")**: continuous vector, dimensionality and meaning depend on which primitive was chosen (listed above).
- **Spatial grounding, defined exactly** (§IV-A): "The selected point *grounds* each primitive in the observed world: the robot action will be applied at a location *relative to* the selected point, as defined by the primitive parameters a^m."
- **The one place geometry deterministically resolves part of the "how"**: for Poke, "the gripper first estimates the surface normal a^norm of the object at a^loc and then goes to the pre-contact location a^preloc = a^loc + a^norm × d1" (d1 = 0.04 m; Appendix -A2). Grasp instead uses a fixed vertical standoff (a^preloc = a^loc + (0,0,d2), d2 = 0.1 m). So only the *standoff offset direction* is geometry-derived (surface-normal-aligned for Poke; world-vertical for Grasp) — the in-plane/approach **orientation angle itself remains a free, learned continuous parameter** inside a^m, not derived from geometry. This is the paper's only "orthogonal-to-surface" mechanism, and it is narrower than a full orthogonal-viewing-direction computation.

**Network / hybrid actor-critic map** (§IV-C): a "segmentation-style point cloud network" (backbone architecture never named explicitly in the text — no PointNet++/sparse-conv/transformer label given, despite four targeted extraction passes) outputs **per-point actor features f_i^a**, shared across all K primitives. Each is fed through a **per-primitive MLP** to produce continuous motion params a^m_{i,k} for every point i and primitive k. These are concatenated with separate **per-point critic features f_i** and passed through an MLP to produce **per-point, per-primitive Q-values Q_{i,k}** — a **K × N "critic map"** over the whole observed point cloud. Discrete action sampling: π_discrete(k, x_i | s) = exp(Q_{i,k}/β) / Σ exp(Q_{i,k}/β) (softmax over the full K×N map at temperature β); at evaluation the argmax point/primitive pair is taken. Trained with **TD3**: critic loss L(φ) = E[(Qφ(s_t,a_t) − y_t)²], actor loss J(θ) = −E[Qφ(f_i, π^θ_{i,k}(s))]. Observations include a **"goal flow"** field: Δx_i = x_i^g − x_i, the per-point 3D correspondence vector from the current point cloud to a goal point cloud (a form of dense, per-point goal-conditioning, not a single global goal vector).

Predecessor: **HACMan** (Zhou et al., CoRL 2023, cited [36]) introduced the "hybrid actor-critic map" concept for a single non-prehensile poking primitive; HACMan++ extends it to a **chainable set of 5 primitives** for longer-horizon tasks.

## Concrete results and numbers

- **DoubleBin task, Table II** (in-text, exact): training-object success **0.892 ± .010** at 30 env steps; **unseen instances of trained categories: 0.952 ± .023**; **unseen categories entirely: 0.849 ± .003** (all at 30-step episode budget; text separately states performance improves "20%+" going from a 10-step to 30-step budget, without a precise paired number).
- **Six simulation tasks** (ManiSkill Lift Cube / Stack Cube / Peg Insertion, Robosuite Pick-and-Place / Door Opening, DoubleBin) are compared against **RAPS** (Dalal et al., NeurIPS 2021, ref [3]) and **P-DQN** (Xiong et al., arXiv 2018, ref [30]) **only in Figure 4** — no exact per-task percentages are given in the running text; the qualitative pattern readable from the figure is that HACMan++'s margin over both baselines is largest on Stack Cube, Peg Insertion, and Door Opening (precision/generalization-heavy tasks) and smallest on Lift Cube (the easiest task). Treat any specific percentage for this figure as an approximate figure-reading, not a citable number.
- **Real-world DoubleBin, Table III** (in-text, exact, 6 objects × 2 goal types × 20 trials = 240 trials total):

  | Object | Same-side | Opposite-side | Subtotal |
  |---|---|---|---|
  | Rubik's Cube | 14/20 | 12/20 | 26/40 |
  | Bowl | 19/20 | 16/20 | 35/40 |
  | Cup | 11/20 | 14/20 | 25/40 |
  | Tennis ball | 19/20 | 19/20 | 38/40 |
  | Cardboard | 11/20 | 15/20 | 26/40 |
  | Toy car | 12/20 | 14/20 | 26/40 |
  | **Total** | **86/120 (72%)** | **90/120 (75%)** | **176/240 (73%)** |

- **Fixed action-space cardinality regardless of object**: N = 400 sampled object points + 1000 background points, K = 5 primitives (values stated in the point-cloud-network description) — the address space size is a hyperparameter of the pipeline, not a function of object geometry or complexity.
- **Real sensing rig**: **4 fixed Azure Kinect cameras**, fused into one point cloud — i.e. the real-world "observed geometry" is itself a **multi-view-fused point cloud**, structurally the same kind of input as our surveyed PLY (fixed external cameras rather than eye-in-hand, but the fusion step is analogous).
- **Sim-to-real domain randomization**: object scale randomized "within a range of [0.8, 1.2]" (proportional). No other randomization details given in the extracted text.
- **Training loop**: 1e4 random actions used to seed the replay buffer; evaluated "every 5e3 environment steps over 20 episodes"; number of parallel environments not stated anywhere in the extracted text.
- **No formal ablation isolating spatial grounding itself.** The paper's evidence that grounding *causes* generalization is the comparison against RAPS (global, ungrounded feature + per-primitive param regression) and P-DQN (regresses a 3D location directly, rather than selecting an observed point) in Fig. 4 — both baselines differ from HACMan++ in more than one respect (architecture, not just presence/absence of grounding), so the causal attribution is argued by analogy/comparison, not isolated by a controlled ablation.

## Load-bearing assumptions

- **Object/background segmentation is a precondition**, stated explicitly as an assumption (§IV): the method never solves segmentation itself; it operates on 𝒳^obj / 𝒳^b as given.
- **A fixed-size point sample (400/1000) stands in for the full geometry.** The address space is defined over *whichever 400 points happen to be sampled from the object this episode*, not over a canonical, object-intrinsic set of locations.
- **The learned policy — not a closed-form geometric rule — decides "where."** Only the Poke primitive's pre-contact standoff *direction* is a deterministic function of local geometry (surface normal); WHICH point to select, and all in-plane orientation angles, come from a trained Q-map / MLP, not from an explicit geometric computation. There is no closed-form "compute the grounded location and its frame from the mesh/cloud" procedure anywhere in the method — grounding is learned, not derived.
- **No canonical object frame or symbolic part vocabulary is assumed or produced.** There is no "face 3," no per-primitive-instance ID, no up-axis convention — everything is indexed by raw point position in an arbitrarily-ordered, per-episode point sample.
- **Real-world validation is single-arm pick/place/poke manipulation on 6 hand/small-scale objects**, not inspection, not viewpoint selection, not camera placement — the 73% success number and its per-object breakdown are not transferable as *numbers* to a viewpoint-quality question; they are evidence about a different task's tolerance for point-cloud-grounded action selection under real sensing noise.

## What transfers to our setting

- **The tuple structure itself is a clean template for a view address, confirming the task's selection rationale — with a precise mapping.** a^prim (primitive *type*, e.g. Poke/Grasp) ↔ our WHAT axis (face-orthogonal vs. cylinder-orbit); a^loc (which grounding point) ↔ our WHERE axis (which primitive *instance*, e.g. face id 3, or which cylinder); a^m (continuous offset/orientation) ↔ our HOW axis (standoff, roll). This directly operationalizes RQ1's classification for our target scheme: it would be class **(b) — object-part reference plus local offset** — with the "part" pinned down as a *symbolic primitive id* rather than HACMan++'s raw point index (our target is coarser/more nameable than HACMan++'s actual instantiation; see negative findings).
- **RQ3, partial and important nuance: the paper does NOT test or support a clean "VLM emits discrete k, geometry emits continuous x_k" split.** All three action components — discrete type, location selection, and continuous parameters — are emitted by the *same* trained network from the *same* forward pass; there is no separation between a symbolic/discrete decision-maker and a deterministic geometric solver. The **only** deterministic-geometry-resolves-pose precedent is narrow: Poke's pre-contact standoff offset (translation only, along the estimated surface normal) is computed from a^loc's local neighborhood, not learned. This is weak but real evidence that *a small piece* of the "how" (standoff direction) can be resolved deterministically downstream of a discrete/near-discrete "where," which is exactly the kind of split RQ3 asks about — but the paper's own design does not go further than that one offset; it does not derive the full pose (including in-plane roll) geometrically. Also note the task's own framing invokes "PAMDP" terminology — the paper never uses that term or gives a formal MDP definition; it cites P-DQN (Xiong et al. 2018, ref [30]) as the source of "discrete-continuous hybrid action space" RL, which is itself in the Masson-et-al./Hausknecht-and-Stone parameterized-action-MDP lineage, but HACMan++ itself does not formalize or cite the PAMDP framing directly.
- **RQ12, a crisp, checkable answer: stable COUNT, not stable MEANING, across objects.** N=400 object-point slots and K=5 primitive slots are identical in *number* for every object the policy ever sees (bowl, cup, tennis ball, cardboard, toy car, Rubik's cube — six geometrically unrelated shapes in the real-robot table alone), but point index *i* carries **no cross-object semantic identity**: point 137 of a bowl's sampled cloud has no relationship to point 137 of a cup's. Generalization (95.2% unseen-instance, 84.9% unseen-category, Table II) is achieved by the *network* learning a location-conditioned function, not by the *address* carrying portable meaning. This is exactly the RQ12 distinction the branch needs, with numbers attached.
- **RQ13/14, positive precedent for a bounded-cardinality guarantee, with a cost.** The action space size (N+background, K) is a fixed hyperparameter regardless of object identity or complexity — "always exactly this many addressable actions" is delivered by construction. The cost, per the point above, is that slot identity is arbitrary/unstable, i.e. bounded cardinality and stable per-slot meaning are shown here to be in tension, not both free — directly informs RQ13's "verify whether slot identity is stable across shapes or arbitrary" (answer for this scheme: arbitrary).
- **RQ9, an existence proof that addressing ACTIONS (not indexing OBSERVATIONS) sidesteps the aspect-graph-style explosion.** HACMan++'s action space is flat and fixed-size (K×N ≈ 5×1400) across arbitrarily varied real and simulated object geometry — no combinatorial blow-up with shape complexity, because the address names a *place to act*, resolved point-by-point from the current observation, rather than an exhaustive enumeration of *qualitatively distinct appearances*. This is a genuine data point (not an argument) supporting the branch's hypothesis that size/indexing pathologies documented for aspect graphs (RQ9 (i)/(iii)) are tied to the observation-indexing framing and may not transfer to an action-addressing framing.
- **RQ16, a distinct point on the build-cost spectrum: purely online, zero offline structure.** There is no precomputed graph, tessellation, or primitive library to "build" ahead of time — the address space (which points exist, their features) is recomputed from scratch every episode/timestep from the current segmented point cloud via one forward pass. Worth recording opposite the Hopf/HEALPix paper's "O(log i), no build phase" and aspect graphs' "expensive offline visual-event computation" as a third cost profile: **per-inference recomputation over the live observation**, with cost proportional to N (fixed at ~1400), not to the object's combinatorial complexity.
- **RQ17, liftable input requirement (real sensing surface): raw segmented point cloud, no CAD/mesh/feature needed.** The real-world instantiation runs on a fused multi-camera point cloud (4 Azure Kinects) exactly analogous in kind to our surveyed PLY — this is evidence that point-cloud-only grounding (no CAD features, no clean mesh) tolerates real sensing noise well enough for 73% task success across geometrically diverse, including irregular (cardboard, toy car), real objects. **What is NOT liftable as software**: no named/off-the-shelf backbone or library is given — the architecture and the RL training loop (TD3 over a hybrid actor-critic map) would need to be reimplemented from scratch; there is nothing here as directly reusable as healpy/H3/MVTorch. What is liftable is the *design pattern* (per-point actor/critic feature map → per-primitive MLP → per-point-per-primitive Q values), not a library call.

## What does NOT transfer, and why (negative findings)

- **This paper contains no cameras, no views, no visibility reasoning, no aspect graph, and no comparison of any kind against a uniform/geometry-agnostic baseline in a perception sense.** None of the reported numbers (73% real success, 0.849–0.952 generalization rates, Table III per-object breakdown) are about view quality or viewpoint selection; they cannot be cited as evidence for or against any RQ about visibility, orthogonality-as-observed, or coverage. Its relevance is 100% structural (the action-tuple template), 0% empirical-for-viewing.
- **a^loc is not "the orthogonal view of face 3" and does not become that with more resolution — it is architecturally a different kind of address.** It is a per-episode index into a locally-sampled point cloud (400 points, resampled/re-segmented every episode), not a stable symbolic reference to a named object part. A blind orchestrator could not "predict what it will get before it moves" from a^loc alone (RQ1's discriminating test) — the mapping from index to 3D location is opaque outside the trained network and the current observation; there is no human/LLM-nameable handle like "face 3" anywhere in the representation. **This is the central negative finding for the branch**: the paper is a template for the *tuple shape* (what/where/how), but its concrete instantiation of "where" is the opposite of what our branch needs (nameable, a-priori-predictable primitive ids) — we would have to replace HACMan++'s raw-point grounding with a symbolic primitive-id grounding to make the template usable, which is a substantive redesign, not a lift.
- **No adjacency, no ordering, no seam-naming, no neighbourhood structure of any kind over a^loc.** Points are treated as an unordered, exchangeable set (a segmentation-network output over a point cloud is permutation-invariant by construction) — RQ4 (ordering), RQ5 (adjacency), and RQ7 (seams) have literally nothing to attach to in this scheme; there is no analogue of "next primitive" or "adjacent face" anywhere in the design.
- **No discrete-region-then-continuous-refinement structure (bears on RQ15).** a^loc is a single point, not a region with area over which a^m then searches — the paper's discrete/continuous split is (primitive type, exact point) discrete-ish and (offset, orientation) continuous, not (named surface region) discrete → (best pose within it) continuous. Our target design (a face as a region, with standoff+roll optimized inside it) is a different discrete/continuous carving than what this paper implements, even though the RQ3 tuple analogy still holds at the type level.
- **No canonical-frame or cross-shape symbolic-consistency machinery is presupposed or discussed (bears on RQ13/RQ20).** Generalization here is purely a learned-network property over raw geometry, not a designed addressing convention with stable per-object-class semantics — so this paper offers **no precedent** for RQ20's specific question (has anyone carried cross-shape *part*-naming consistency through to naming actions/views with stable meaning). It reinforces, rather than closes, the gap RQ20 asks about: even a paper explicitly built around cross-object generalization of a spatially-grounded action space does not attempt symbolic per-slot naming — it sidesteps the naming problem entirely by making addresses opaque/positional and leaning on network generalization instead.
- **No treatment of infeasibility, IK/collision failure, or "nearest feasible" fallback for a chosen address** (bears on RQ16 in the original task list, "does the addressing scheme survive infeasibility"). The paper does not discuss what happens if a selected a^loc + a^m pair is kinematically unreachable; no precedent to hand to Branch 4 from this document.
- **No discussion of geometric failure localization.** The one sentence on struggling categories ("some categories with which our method struggles because of the irregular geometries," Appendix B5 / Fig. 14) is not elaborated with specific geometric conditions (edges, concavities, occlusion) — cannot be used as evidence for RQ7's seam-naming question or for edge/corner failure characterization.

## Assessment for the branch

HACMan++ earns its place in this branch as a **structural analogy, not a viewpoint paper**: the (type, grounding-location, continuous-parameters) tuple is a genuinely clean precedent for the (face-orthogonal|cylinder-orbit, primitive id, standoff+roll) shape our target address needs, and it comes with real numbers showing that grounding a discrete/continuous hybrid action on a *currently observed*, possibly-noisy, real-sensed point cloud (4 fused Kinects, scale-randomized sim-to-real) works well enough in practice (73% real success across 6 varied objects) to trust the general pattern. But its concrete "where" mechanism — an opaque per-episode index into a fixed-size raw point sample, with stable *count* but zero cross-object *meaning*, no adjacency, no ordering, no canonical frame, and no symbolic nameability — is close to the opposite of what RQ1/RQ2 need from an address a blind orchestrator can predict before moving. The actionable takeaway for RQ3/RQ12/RQ13 is precise: **borrow the tuple shape, replace the "where" mechanism wholesale** with a symbolic primitive-id grounding (not HACMan++'s point-cloud index), and treat the one deterministic-geometry precedent in this paper (surface-normal-aligned standoff offset for Poke) as weak but real support for resolving at least part of the continuous "how" geometrically downstream of a discrete choice, rather than learning all of it end-to-end as HACMan++ does.
